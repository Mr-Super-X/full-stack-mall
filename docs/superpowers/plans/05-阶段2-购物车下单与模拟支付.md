# 阶段 2 后端实施计划（下半场）：购物车 + 下单 + 模拟支付（2026-11-09）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> **执行方式**：主会话逐文件实现（native），每个文件完成后自检并回看本计划；验收环节 curl + 浏览器实操。

**Goal**：买家侧闭环走通——加购（仅自营）→ 购物车结算或寄卖直购 → 下单（快照 + 条件更新扣库存）→ FakeProvider 支付（收银台 + 回调幂等）→ 订单转已支付；超时未支付惰性关单还库存。阶段 2（⭐MVP）就此完整。

**Architecture**：新增 `cart/`、`order/`、`payment/` 三个业务包。下单是单一 `@Transactional`：建订单（type=NORMAL）+ 建明细（**快照 JSON 定格下单瞬间**）+ **条件更新扣库存**（`UPDATE...SET stock=stock-q WHERE id=? AND stock>=q`，行数 0 即回滚抛库存不足）+ CART 模式清购物车行；支付走 `PaymentProvider` 抽象（Fake 实现本地闭环：验签用 md5(paymentNo+amount+secret) 模拟支付宝同款流程），回调幂等靠 **paymentNo 查库 + 状态机单向（CREATED/PAYING→SUCCESS，已 SUCCESS 直接返回）+ 金额校验 + 订单 PAID 条件迁移**四件套；惰性关单在订单查询时触发（超时未支付 → CANCELLED + 还库存，同事务）。

**Tech Stack**：沿用现有（Java 17 / SB 3.5.9 / MP 3.5.18.1 / MySQL 8.4 / jjwt 0.12.6 / 本机 Maven）；无新依赖。

**Spec**：[../specs/2026-11-06-resale-mall-design.md](../specs/2026-11-06-resale-mall-design.md)（§4.4 快照铁律、§4.5 钱的两条线、§6 接口契约（购物车/订单/支付）、§7 决策 1/2/3、精讲契约 2 幂等三件套、§12.1 决策 6-9）

**前置契约**（已交付）：`UserContext.getRequired()`；条件更新范式（plan-04 migrateStatus）；`ProductItemMapper`（stock/version）；地址 CRUD（addressSnapshot 来源）；双层拦截器（本计划把 `/mall/cart/**`、`/mall/orders/**`、`/mall/payments/**` 挂入 AuthInterceptor——支付 notify 回调路径**例外放行**（网关调用无 Cookie，靠验签鉴权））。

## 与原计划相关的设计决策（已定，读者必读）

| 项 | 决策 | 理由 |
|---|---|---|
| 订单 type 取值 | 寄卖直购订单 `type=NORMAL` | type 是玩法维度（普通/秒杀/众筹/订阅）不是货源维度；货源由 OrderItem.sellerId 区分 |
| DIRECT 直购范围 | **仅寄卖**（ownerType=CONSIGNMENT）；自营直购一律走购物车 | 避免两条购买路径都全功能；寄卖库存恒 1 进购物车会堆积失效商品 |
| 支付单创建时机 | 下单同事务创建（CREATED，返回 paymentNo） | 简化前端流程：下单即拿 paymentNo 直接发起 pay |
| Fake 收银台 | `GET /mall/payments/fake/checkout` 返回极简 HTML（金额 + "完成支付"按钮 POST notify） | 闭环可视化（浏览器点一下走完整回调链），教学价值高 |
| 订单号 | `"M" + yyyyMMddHHmmss + 4位随机`，uk 冲突重试 3 次 | 已拍板；冲突概率极低，重试逻辑演示用 |
| notify 路径放行 | `/mall/payments/fake/notify` 不挂 AuthInterceptor | 模拟支付宝服务器→商户服务器的回调，无用户 Cookie，鉴权靠验签 |

## Global Constraints

- 信封 code=200 成功；业务错误 HTTP 仍 200
- 新增错误码：`STOCK_NOT_ENOUGH(400,"库存不足")`、`ORDER_STATE_ILLEGAL(400,"当前订单状态不允许该操作")`、`PAYMENT_STATE_ILLEGAL(400,"当前支付状态不允许回调")`、`CONSIGNMENT_DIRECT_ONLY(400,"寄卖商品请直接购买")`、`ORDER_NOT_FOUND(404,"订单不存在")`、`PAYMENT_NOT_FOUND(404,"支付单不存在")`
- **快照铁律**：OrderItem 存 `item_snapshot` JSON（title/imageUrl/conditionGrade/size/color/brand/ownerType）+ `price`（成交价）；订单展示永不回联商品实时数据
- **条件更新防超卖**：`UPDATE product_item SET stock=stock-q, version=version+1 WHERE id=? AND stock>=q`，影响行数 0 → 抛 STOCK_NOT_ENOUGH 触发整体回滚；字符串 UpdateWrapper（同 plan-04 Ruling）
- **幂等四件套**：验签 → paymentNo 查库 → 状态机单向 → 金额校验（不等 → 400 + 日志）
- 订单越权：他人订单按 404（同寄卖口径）
- expiredAt = createTime + 15 分钟（常量 `ORDER_EXPIRE_MINUTES = 15`）
- Entity 不出 Controller；单文件 ≤400 行；公共 API 中文 Javadoc
- 金额一律 BigDecimal；JSON 互转集中 Service 层 Jackson（同 plan-04 模式）

## Review Focus（最易咬人的 6 处）

1. **并发超卖**：两个请求同时抢寄卖单件（stock=1）→ 条件更新只放行一个，另一个 STOCK_NOT_ENOUGH 回滚——OrderServiceImplTest 用 mock update 返回 0 断言
2. **快照铁律**：下单后商品改价/改名，订单详情仍显示快照价与快照标题——e2e 断言（下单 → SQL 改价 → 详情价格不变）
3. **回调幂等**：同一 paymentNo 连续两次 notify → 第二次返回成功但订单/sales 不重复推进（条件迁移行数 0 则跳过 sales 累加）——PaymentServiceImplTest 断言
4. **金额篡改**：回调 amount 与应付不等 → 400 且记日志，订单不推进
5. **惰性关单**：造一个 expiredAt 已过的 PENDING_PAYMENT 订单，查询后变 CANCELLED 且库存回补；关单后到达的 notify → 拒绝（400）——e2e 验证
6. **寄卖加购拦截**：ownerType=CONSIGNMENT 的 productItem 加购 → 400 "寄卖商品请直接购买"
