## 1. 意图与为什么

阶段 4a 用「DB 条件更新」跑通了秒杀业务闭环（正确性优先）。4b 回答的问题：**为什么需要 Redis？什么时候 Redis 也不够？**

答案形态不是"Redis 赢了"，而是：
- **拐点曲线**：DB 版在哪个并发点开始 P99 爆炸、成功率归零；Redis 版在哪个点开始暴露自己的问题（单点瓶颈 / 预扣成功但落库失败的少卖）。
- **一致性对照表**：正常 / Redis 挂 / 落库失败 / 重复消费四种场景下，超卖、少卖、重复扣各发生几次。
- **兜底时序图**：每个环节的"挂了会怎样、怎么兜"都画得出、答得上。

**为什么把"异步落库"做成完全异步（排队出单）而不是预扣+同步建单**：
- 完全异步才有真实的「落库失败」「重复消费」「死信」场景——一致性对照表的三行靠它成立；
- 这是 12306 / 小米秒杀的真实形态，故事完整度与压测曲线张力都更强；
- 同步建单方案的「落库失败」只能降级为「对账补偿」，对照表故事弱一档（已权衡，用户拍板选完全异步）。

### 2.2 非目标（明确不做）

- **Sentinel 等独立限流组件**：用 Redis Lua 令牌桶（与本期 Redis 引入一致，故事聚焦）；
- **Redlock / 分布式锁**：单 Redis 实例规模下是复杂度不是收益——这是第三层取舍声明的落字点，不做；
- **Redis 宕机降级到 DB**：宁可拒绝服务不可超卖（取舍声明点）；降级会让一致性语义分裂、对照表讲不清；
- **多实例水平扩展压测**：单实例压出拐点即可，多实例是面试追问的答案不是本期工程；
- **真实支付/真实队列上云**：FakeProvider + 本地 RabbitMQ 闭环。
- **搜索/其他模块的缓存化**：4b 的 Redis 只服务秒杀（边界清晰，README 演进故事干净）。

## 3. 总体形态：配置开关 + 三实现

```yaml
# application.yml
seckill:
  strategy: redis        # optimistic（默认=4a 行为）/ pessimistic / redis
  rate-limit:
    capacity: 200        # 令牌桶容量（初始值，压测后校准并更新注释）
    refill-per-second: 100
  mq:
    consumer-simulated-failure-rate: 0   # 故障注入：消费者落库失败率 0~1（0=关闭）
```

`SeckillServiceImpl.placeOrder` 按 `strategy` 分派两条路径：

| strategy | 扣减 | 建单 | 返回 |
|---|---|---|---|
| `optimistic` | `deductStock` 条件更新（4a 原样） | 同步事务（4a 原样） | `{orderNo, paymentNo}` |
| `pessimistic` | 事务内 `SELECT ... FOR UPDATE` 锁行后判库存 | 同步事务 | `{orderNo, paymentNo}` |
| `redis` | Redis Lua 预扣（§4） | **异步**：发 MQ（§5），受理即返 | `{orderNo, status: "ACCEPTED"}` |

**契约不变量**：四错误码（40001/40002/40003/40004）三实现通用；`redis` 模式新增受理语义，`GET /mall/seckill/orders/{orderNo}` 为新增端点（§5.4）。

## 4. Redis 预扣设计

### 4.1 键设计（基准文档 §12.3 待定项，本期定案）

| Key | 类型 | 写入 | 删除 | 语义 |
|---|---|---|---|---|
| `seckill:stock:{activityId}` | String（剩余库存数） | 活动激活时 `SET`（= seckill_stock − sold_count）；下单 Lua `DECR` | 活动推进 ENDED/CANCELLED 时 `DEL` | 预扣唯一关口 |
| `seckill:order:{activityId}:{userId}` | String（orderNo 占位） | 预扣成功后 `SET NX EX 900`（15 分钟 = 订单超时） | TTL 自然过期 / 关单回补后 `DEL` | 限购体验层加速（Redis 挡 40003）；DB uk_user_activity 仍是并发兜底真相 |

**裁决：不设 sold 计数 key**——进度条读 sold_count 仍走 DB（秒杀进行中读流量远小于写，且 DB 已有一致真相）；Redis 只承担"扣减关口"单一职责，键越少故事越清。

### 4.2 Lua 预扣脚本（原子性核心）

```lua
-- KEYS[1] = seckill:stock:{activityId}
-- KEYS[2] = seckill:order:{activityId}:{userId}
-- ARGV[1] = orderNo（占位值，同时充当幂等痕迹）
local stock = tonumber(redis.call('GET', KEYS[1]) or -1)
if stock < 0 then
  return -1            -- 活动未初始化或已结束：视为不可售（40001 语义由调用方活动校验先兜）
end
if stock == 0 then
  return 0             -- 抢完：40002
end
if redis.call('SET', KEYS[2], ARGV[1], 'NX', 'EX', 900) == false then
  return -2            -- 已占位：40003
end
redis.call('DECR', KEYS[1])
return 1               -- 预扣成功
```

- **三个分支一次 RTT**：超卖在 Redis 层物理不可能（DECR 前判 stock>0 原子完成）；
- 活动校验（40001 语义）仍在 DB 读路径完成（4a 第 1-3 步不变），Redis 只挡"扣"这一刻；
- **key 缺失自愈**：Lua 返回 -1（key 不存在）时，调用方以 DB 当前值 `SET seckill:stock:{id} (seckill_stock - sold_count) NX` 重建一次再重试——DB 是真相源，关口补建不引入新语义；重建后仍 -1 才报 40001（活动未初始化 = 校验漏拦的防御分支）；
- 占位 key TTL = 订单超时：关单后资格不释放（4a spec §10#3 固化行为的延续），TTL 兜底防 Redis 残留。

### 4.3 初始化与回补（生命周期）

| 时机 | 动作 | 实现位 |
|---|---|---|
| 活动激活（惰性 activateIfDue 成功时） | `SET seckill:stock:{id} seckill_stock - sold_count` | `SeckillServiceImpl.activateIfDue` 后插 Redis 初始化（strategy=redis 时） |
| 下单预扣 | Lua（§4.2） | `RedisStockDeductor.deduct` |
| 订单超时关单（惰性） | DB 回补独立池（4a 既有）+ Redis `INCR seckill:stock:{id}`（若 key 还在） | `OrderServiceImpl.restock` 秒杀分支扩展 |
| 活动推进 ENDED/CANCELLED | DB 归还（4a 既有）+ Redis `DEL` | `settleEnded` / admin cancel 扩展 |

**回补失败容忍**：Redis 不可用时 INCR/DEL 失败只记 warn 日志不阻断 DB 事务——Redis 只是关口，DB 仍是真相；下次激活路径会重建 key。

### 4.4 Redis 挂了怎么办（对照表第 2 行）

- **行为**：Lua 预扣抛连接异常 → 全局异常处理器转 503 + 业务码 `SECKILL_UNAVAILABLE`（新增 40005）→ 前端 toast「秒杀服务暂不可用」；
- **取舍**：**不降级到 DB**——降级会让"已扣 Redis 的请求"与"直接落 DB 的请求"并发写独立池，sold_count 真相分裂，宁可拒绝不可超卖（取舍声明落字 §14）。

## 5. RabbitMQ 异步出单设计

### 5.1 队列拓扑

```
seckill-order-create.exchange (direct, durable)
    │ routingKey = seckill.order.create
    ▼
seckill-order-create.queue (durable)
    │ x-dead-letter-exchange = seckill-order-create.dlx
    │ x-message-ttl = 300000（5min，给重试留窗口）
    ▼ 消费失败 nack requeue=false → 重试 3 次（消费者计数）→ 进入
seckill-order-create.dlx (fanout)
    ▼
seckill-order-create.dlq (durable)   ← 死信=少卖，对账/人工回补入口
```

### 5.2 消息格式（JSON）

```json
{
  "orderNo": "M202611101430001234abcd",
  "activityId": 16,
  "userId": 3,
  "productItemId": 1601,
  "addressId": 7,
  "seckillPrice": 299.40,
  "deductedAt": "2026-11-10T14:30:00"
}
```

- `orderNo` 在 **Controller 层预生成**（受理即生成，响应与消息同源）；
- 消息幂等键 = `orderNo`（消费者查重：`SELECT 1 FROM orders WHERE order_no=?` 存在即 ack 跳过）。

### 5.3 消费者事务（`SeckillOrderCreateConsumer`）

```
onMessage:
  1. 幂等查重（orderNo 已存在 → ack）
  2. @Transactional：复用 4a 建单三步——insertSeckillOrder（orderNo 预置不再重试生成）
     + buildSeckillLine + insertPayment
     撞 uk_user_activity → 转 40004 语义（记日志 ack，消息不回流——重复消费场景落字）
  3. 失败（非幂等类）→ nack + requeue 计数；第 3 次进 DLX
  4. 故障注入：seckill.mq.consumer-simulated-failure-rate > 0 时按概率抛异常
```

**与 4a 的复用关系**：`insertSeckillOrder` / `buildSeckillLine` / `insertPayment` 三个私有方法抽成 `SeckillOrderAssembler`（package-private），4a 同步路径与 4b 消费者共用——**两套路径同一套建单代码，对照实验的公平性前提**。

### 5.3b 受理与发送时序（关键路径，时序图底稿）

```
placeOrder（strategy=redis 同步段）：
  1. DB 事务：校验（4a 第 1-4 步）+ Redis Lua 预扣（事务外先行，见下）+ 受理记录落库（seckill_order_acceptance，status=ACCEPTED）
  2. 事务提交后：发送 MQ（必须提交后——否则出现"消息已发但受理回滚"的幽灵订单）
  3. 发送失败补偿：Redis INCR 回补 stock + 受理记录置 FAILED（新事务）+ 返回业务错误（40005 家族，语义=受理未成立）
```

> **时序裁决**：Lua 预扣在 DB 事务**外**先行执行（Redis 不参与 DB 事务，无 2PC）；DB 事务回滚（校验失败/DuplicateKey）时补偿 INCR 回补 Redis——同一取舍：Redis 是关口不是真相，INCR 失败仅 warn。
> **MQ 挂场景归类**：发送失败 = 同步段失败（响应错误），与 §8 对照表"Redis 挂"行同列处理；消费者挂/慢由 TTL+DLX 覆盖，不新增对照表行。

### 5.4 轮询端点（新增契约）

| 接口 | 说明 |
|---|---|
| `GET /mall/seckill/orders/{orderNo}` | 登录态。受理中 `{status:"ACCEPTED"}`；建单完成 `{status:"CREATED", paymentNo}`；DLX 登记失败 `{status:"FAILED"}`（orderNo 找不到对应单时回退查受理登记表，见下） |

**受理登记表**：`seckill_order_acceptance` 新表（`order_no` uk / `activity_id` / `user_id` / `status` ACCEPTED/FAILED / `create_time`），受理时同步写入，消费者成功后置 CREATED（订单表可查后此表仅作审计）。FAILED 状态由 DLX 监听器登记——**前端轮询到 FAILED 提示「抢购失败，库存将回补」**。

> 裁决：受理表落库而非纯内存 Map——重启不丢受理记录，对照表"少卖数"有据可查（`status=ACCEPTED` 且无对应订单 = 少卖）。

### 5.5 少卖的定义与对账（对照表口径）

| 场景 | 少卖数口径 | 回补动作 |
|---|---|---|
| 消息重试 3 次失败进 DLX | DLQ 深度 | DLX 监听器：DB `sold_count-1`（条件防负）+ `INCR seckill:stock:{id}` + 受理表置 FAILED |
| Redis 预扣成功但发送 MQ 前 JVM 崩溃 | `受理表 ACCEPTED & 无订单 & 消息不存在`（对账 SQL） | 定时对账任务（本期为 SQL 脚本，不做调度器——与惰性哲学一致） |
| Redis 宕机无持久化丢预扣 | 无法自动感知（取舍声明点 §14） | 人工按受理表对账 |

## 6. 限流设计（Redis 令牌桶）

- **实现**：`seckill:rate-limit:{userId-or-ip}` Lua 令牌桶（单 key 单用户级 + 全局活动级双层）；
- **挂载点**：`SeckillController` 下单路径方法级切面（`@RateLimit` 注解 + AOP）；
- **参数依据**：初值 capacity=200/refill=100，**压测后按"DB 拐点并发的 70%"校准并更新注释**（参数不是拍脑袋的证据链落字）；
- **被限流的响应**：429 语义 + 业务码 `RATE_LIMITED`（40006），JMeter 结果里计入失败。

## 7. 悲观锁对照组（FOR UPDATE）

```java
// strategy=pessimistic 分支（嵌在 placeOrder 事务内，替换 deductStock）
SeckillActivity locked = mapper.selectForUpdate(activityId);  // SELECT ... FOR UPDATE
if (locked.getSoldCount() >= locked.getSeckillStock()) throw SOLD_OUT;
mapper.incrSoldCount(activityId);
```

- 行锁串行化扣减，故意保留**锁等待/死锁风险**——它就是用来在曲线上炸掉的；
- 压测时的锁等待超时（innodb_lock_wait_timeout 默认 50s）调小至 5s，让拐点在 500 线程内可见；
- **作用域**：docker-compose MySQL 全局 `command: --innodb-lock-wait-timeout=5`，教学库常态生效不恢复（本库无其他业务流量）；README 标注该参数为压测环境配置，生产含义另述。

## 8. 一致性对照表（验收产物）

| 场景 | 注入手段 | 超卖 | 少卖 | 重复扣 | 预期结果 |
|---|---|---|---|---|---|
| 正常路径 | — | 0 | 0 | 0 | Redis 扣数 = DB sold_count = 成功单数 |
| Redis 挂 | `docker pause mall-redis` | 0 | N（请求全拒） | 0 | 全部 40005，DB/Redis 零写入 |
| 落库失败 | `consumer-simulated-failure-rate=1` + 3 次重试进 DLX | 0 | =DLQ 深度 | 0 | DLX 回补后最终一致 |
| 重复消费 | DLX 消息手动 requeue | 0 | 0 | 0 | 幂等查重拦截，ack 即弃 |

**产出形式**：README/作品集里的表格 + 每组场景的 JMeter 报告截图 + 对账 SQL 输出。

## 10. h5 前端改动（轮询出单）

1. `h5SeckillApi.placeOrder` 响应类型扩展：`{orderNo, paymentNo?}` → 判别 `paymentNo` 是否存在；
2. 结算页秒杀提交分支：无 `paymentNo` 时进入「受理中」态（按钮 loading + 文案「排队出单中…」），`setInterval 1s` 轮询 `GET /mall/seckill/orders/{orderNo}`，上限 15s：

   - `FAILED` → 清定时器，toast「抢购失败，库存已回补」；
   - 超时 → toast「出单超时，请至订单页查看」（受理单可能仍在消费，兜底不丢单）；
3. 轮询 composable `useSeckillOrderPolling`（≤80 行，带 spec）；
4. mock 处理器对齐受理/创建两态（`check:mock-wiring` 保持绿）。

## 12. 验收标准（独立测试依据）

1. **三曲线数据齐**：五档并发 × 三实现，每组成功率/P50/P99/超卖/少卖五指标齐全，JMeter 原始报告入 git（benchmark/results/）。
2. **拐点可见**：pessimistic 在 ≤500 线程内出现 P99 爆炸或成功率骤降；redis 拐点若未出现，结论如实写「500 线程内未达拐点，推断点>500」——**不编造数据**。
3. **一致性四场景**：§8 表格四行全部实测填数，超卖列全 0。
4. **异步链路幂等**：同一消息手动 requeue 10 次，订单表仍只有一单（40004 语义），无重复扣。
5. **四错误码不回退**：redis 模式下 40001/40002/40003/40004 各路径独立用例通过（40003 双通道：Redis 占位 + DB uk）。
6. **前端闭环**：结算页提交 → 受理中 → 轮询 → 收银台支付 → 订单页可见，与 4a 体验对齐。
7. **对账恒等式**：每组压测后 `reconcile.sql` 输出满足 `DB sold_count = 成功订单数 = Redis 预扣数 − DLQ 深度 − 受理未出单数`。

## 13. 裁决清单（builder 无需追问）

| # | 裁决 | 理由 |
|---|---|---|
| 1 | 完全异步出单（受理即返，消费者建单） | 用户拍板；12306/小米形态；对照表三行场景靠它成立 |
| 2 | RabbitMQ（docker-compose 新增） | 用户拍板；死信/持久化开箱即用，management 插件可截图 |
| 3 | JMeter 压测（jmx 进 git） | 用户拍板；GUI 报告作品集友好；CSV 参数化三趟复用 |
| 4 | 配置开关切换三实现 | 用户拍板；「同一契约三实现」本身是叙事点 |
| 5 | Redis 只设 stock + 占位两 key，sold 计数留在 DB | 键越少职责越清；进度条读流量小，DB 扛得住 |
| 6 | 预扣占位 key TTL=15min 对齐订单超时 | 与关单节奏一致；TTL 兜底防 Redis 残留 |
| 7 | 关单/结束回补 Redis 失败仅 warn 不阻断 DB 事务 | Redis 是关口不是真相；下次激活重建 key |
| 8 | Redis 宕机拒绝服务（40005）不降级 | 取舍声明点；降级会让双写真相分裂 |
| 9 | 受理登记表落库（seckill_order_acceptance） | 重启不丢受理；少卖口径有据；FAILED 状态有载体 |
| 10 | 建单三步抽 SeckillOrderAssembler 供同步/异步共用 | 对照实验公平性前提：两条路径同一建单代码 |
| 11 | 限流参数初值 200/100，压测后按「DB 拐点并发 70%」校准 | 「参数来自压测」的证据链落字，非拍脑袋 |
| 12 | pessimistic 分支 innodb_lock_wait_timeout 调小到 5s | 500 线程内可见拐点（教学项目体量） |
| 13 | 对账本期为 SQL 脚本不做调度器 | 与惰性哲学一致；对账频率需求低 |
| 14 | DLX 监听器自动回补（sold_count-1 + INCR stock + FAILED 登记） | 死信不人工介入也能收敛；人工只处理 Redis 宕机类 |
| 15 | 压测账号 500 个 = 最大并发档；库存沿用 4a 基线 10 件 | 限购=1 下账号数 ≥ 并发档才不会被 40003 污染口径；10 件口径与 4a 数据可对比（builder-check 问题 1） |
| 16 | 受理记录与 Redis 预扣同 DB 事务，MQ 发送在提交后；发送失败补偿 INCR + 受理表 FAILED | 避免幽灵订单；受理表即本地消息表简化形态（builder-check 问题 2） |
| 17 | Redis stock key 缺失时下单路径 SET NX 从 DB 重建一次再重试 | DB 是真相源，关口补建不引新语义；-1 只作防御分支（builder-check 问题 3） |
| 18 | lock_wait_timeout 5s 作用于 docker-compose 全局并常态生效 | 教学库无其他业务；README 标注防误读（builder-check 问题 4） |

## 14. 取舍声明（第三层证据链，README 落字）

> **「我的方案在哪里会坏」——阶段 4b 已知取舍**
>
> 1. **最终一致，宁可少卖不超卖**：Redis 预扣 + 异步落库在「Redis 宕机且无 AOF 持久化」的极端场景下，预扣记录丢失 → 少卖且无法自动感知，需人工对账。选择理由：超卖 = 资损 + 客诉，少卖 = 损失一次成交，代价不对称。要强一致需 Redis 事务 + DB 本地消息表，吞吐掉约 X%（压测实测后填数）。
> 2. **不做 Redlock**：单 Redis 实例下分布式锁带来的复杂度大于收益；扩多实例时的演进路径是 Redis Cluster + 槽位亲和，不在本期。
> 3. **限流会误伤**：令牌桶超发时的 429 对真实用户不友好，本期取舍是「保护系统优先」；演进方向是按用户画像分级限流。
> 4. **500 线程不是 Redis 的拐点**：单实例 Redis + 本机 Docker 的瓶颈先在网络与连接池；真实拐点需要更大压测环境——本期如实标注「>500 未测」。
