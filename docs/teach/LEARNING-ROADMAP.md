# 前端工程师的后端与部署掌控路线

> 文档性质：上一轮学习建议的正式落盘版本，并与仓库已有 `teach` 课程整合。
>
> 日期：2026-11-20。依据为当前仓库的 README、后端依赖与配置、Compose 编排、独立部署文档，以及 Docker Compose 官方文档。本次未实际启动服务或操作服务器。

## 一、核心结论

**不要先脱离项目系统学习整个 Java 生态，也不要从秒杀、Redis、RabbitMQ 开始。**

以当前项目为实验场，沿真实请求和真实部署做纵向切片：

```text
启动观察 → 读通接口 → 理解鉴权 → 掌握数据与事务
→ 完成业务闭环 → 学习异步与高并发 → 部署、恢复与回滚
```

这里的“掌控”不是能背技术名词，而是六种可观察能力：

| 能力 | 过关标准 |
| --- | --- |
| 启动 | 能启动全栈，解释服务作用、端口、配置和依赖关系 |
| 读通 | 能画出一个接口从浏览器到数据库再返回的完整链路 |
| 修改 | 能完成一个纵向小需求，说明每层为何需要或不需要修改 |
| 验证 | 能运行已有测试、构造异常输入、查看日志并区分事实与推测 |
| 部署 | 能从干净环境构建并启动，理解镜像、网络、数据卷和健康检查 |
| 运维 | 能验证备份、在测试环境恢复、回滚，并处理常见启动和访问故障 |

**看懂代码不等于掌控；能预测、验证、解释和恢复才算。**

## 二、先建立两张地图

### 1. 运行地图：请求经过哪些进程

当前根目录全栈编排如下（`README.md:81`、`docker-compose.yml:53`）：

```text
浏览器
  → Nginx :8080
      ├─ /h5、/admin 等：前端静态文件
      └─ /api：反向代理到 Spring Boot :18080
                         ├─ MySQL：业务数据
                         ├─ Redis：Lua 原子扣减、限流
                         └─ RabbitMQ：异步出单、重试和死信处理
```

第一轮应能回答：

- 为什么浏览器只访问 `8080`，后端进程却监听 `18080`？
- `/api` 在哪里配置，Nginx 又把它转发到哪里？
- 为什么本机开发数据库使用 `localhost:13306`，容器内却使用 `mysql:3306`？
- 容器停止、容器删除、镜像删除和数据卷删除分别意味着什么？
- `depends_on: service_healthy` 保证了什么，又不能保证什么？

本仓库同时存在两种开发／运行形态，不能混用命令：

| 形态 | 入口 | 后端在哪里运行 | 主要用途 |
| --- | --- | --- | --- |
| 全栈容器 | 根目录 `docker-compose.yml` | `backend` 容器 | 完整体验、部署形态学习 |
| 本地开发 | `backend/docker-compose.yml` | 本机 `mvn spring-boot:run` | 修改代码、运行测试、调试 |

### 2. 代码地图：一个接口经过哪些层

先选择商品列表这种只读接口：

```text
HTTP 请求
  → Interceptor：按路径决定是否鉴权
  → Controller：接收参数、定义 HTTP 接口
  → Request DTO：描述输入契约
  → Service：实现业务规则
  → Mapper：执行数据访问
  → Entity：映射数据库记录
  → Response DTO：描述输出契约
  → Result：统一响应信封
```

需要理解的不是注解清单，而是：

- 每层的输入、输出、职责和不应该承担的职责；
- 哪些数据来自前端，哪些身份数据只能由服务端鉴权获得；
- 数据库字段如何变成前端收到的 JSON；
- 参数错误、空结果、业务失败和未知异常分别如何处理。

Java、HTTP、SQL、Maven、Spring 和 MyBatis 都按这条链路的需要补最小知识，不另起一个无限扩张的“先修课清单”。

## 三、学习顺序与阶段验收

### 阶段 1：启动与观察

学习服务、容器、端口、网络、卷、环境变量和健康检查。先使用只读或保留数据的操作，建立观察习惯。

**过关实验：**只停止再启动后端，观察前端请求从正常到失败再恢复，并用容器状态与日志解释，而不是靠猜。

### 阶段 2：只读接口与鉴权

先读商品列表，再读登录、`AuthInterceptor`、`UserContext` 和 `AdminInterceptor`。

重点问题：

- 401 与 403 分别在哪里产生？
- 为什么使用 JWT + HttpOnly Cookie？
- 为什么支付回调不走用户 Cookie 鉴权，而要走验签？
- 为什么 `UserContext` 必须在请求完成后清理？

### 阶段 3：数据库、事务与支付

先理解表、唯一键、快照和约束，再进入下单和支付：

- 下单为什么需要事务，事务边界包含哪些写入？
- 为什么扣库存不能先查再写？
- 为什么订单商品保存快照，而不是永远回查实时商品？
- 用户重复点击、支付重复回调时，哪一层阻止重复副作用？
- 业务异常为什么不在 Controller 中各自拼装响应？

### 阶段 4：完成业务闭环，再学习高并发

先理解寄卖、订单履约、确认收货和结算，再学习秒杀三策略、Redis 和 MQ。

高并发阶段必须问清：

- 乐观锁和悲观锁分别解决了什么，又牺牲了什么？
- Redis Lua 为什么能作为原子扣减关口？
- 为什么数据库事务提交后才发送 MQ？
- ACK、重试、死信、幂等和库存回补如何配合？
- “最终一致”期间用户看到什么，如何对账和恢复？

### 阶段 5：部署、备份、恢复与回滚

围绕以下真实文件学习，而不是只记命令：

- `backend/Dockerfile:5`：Maven 构建与 JRE 运行的多阶段镜像；
- `docker-compose.yml:53`：服务依赖、环境变量、容器网络和健康检查；
- `deploy/README.md:21`：前后端独立部署顺序；
- `deploy/backend/README.md:71`：MySQL 备份、恢复及其边界；
- `deploy/frontend/README.md:98`：前端镜像备份与回滚。

完整流程必须走通：

```text
配置检查 → 构建 → 启动 → 健康检查 → 业务接口验证
→ 日志观察 → 备份 → 测试环境恢复 → 回滚 → 再验证
```

## 五、怎样提问最有效

避免“给我讲讲整个后端”“Spring Boot 怎么学”这类没有边界的问题。使用下面的模板：

```text
我是有 Vue / TypeScript 经验的后端初学者。
请只基于当前仓库和 docs/teach/RESOURCES.md 回答，先不要修改代码。

本次目标：理解【一个具体接口或部署问题】。
范围限制：只讲【指定链路】，暂时不要扩展到其他高级主题。

请输出：
1. 按真实执行顺序列出调用链，并给出 file_path:line_number。
2. 说明每一层的输入、输出、职责，以及它不应该负责什么。
3. 给出一个具体请求或操作示例，逐步说明数据如何变化。
4. 分别说明正常、失败、重试或恢复路径。
5. 指出我必须掌握的三个概念；可以用前端知识类比，但要说明类比边界。
6. 给我一个最小验证实验，包括预测、操作、预期结果和观察位置。
7. 区分代码已确认事实、官方文档事实和尚未验证的推测。

最后向我提三个检查理解的问题，先不要公布答案。
```

### 让 AI 分三种角色工作

1. **讲解员**：基于真实代码和一手文档解释。
2. **提问者**：只追问预测、依据和边界，暴露理解漏洞。
3. **验收者**：检查真实输出，区分“已执行、未执行、结果不符”。

不要让同一个“直接给我答案”的提示同时替代这三种角色。

## 六、学习方法论

### 1. 纵向切片，不横向刷完整技术栈

沿“商品列表 → 登录 → 数据库 → 下单 → 支付 → 结算 → 秒杀 → 部署”推进。每个主题都经历运行、阅读、预测、验证和教回。

### 2. 先预测，再运行

实验前写下预计结果及代码／配置依据。预测错误不是失败，而是发现心智模型漏洞的最有价值时刻。

### 3. 一次只改变一个变量

接口不通时，不要同时修改端口、CORS、Nginx、鉴权和数据库。按链路逐段收集证据：

```text
浏览器 → Nginx → 后端进程 → 拦截器 → Controller → Service → 数据库
```

### 4. 正常、失败、恢复三条路径一起学习

后端难点通常不在成功响应，而在重复请求、并发、部分失败、超时和恢复。每节课至少研究一个失败场景。

### 5. 用提取代替重复阅读

合上书重画链路、做不同场景的题、向 AI 教回。熟悉感不是掌握，费力但正确的提取才形成长期记忆。

### 6. 用输出检验理解

每个主题只保留三类高价值笔记：

- 一张自己画出的链路或状态图；
- 一份经过实际验证的命令与结果记录；
- 一份故障记录：症状、证据、根因、修复和预防措施。

## 七、综合实战：最终验收项目

完成课程后，用两个小型综合任务验证是否能脱离教程工作。

### 实战 A：一个纵向业务改动

选择经学习者确认的窄需求，例如给商品列表增加一个明确的只读筛选条件。学习者需要先写验收标准，再独立完成：

```text
接口契约 → 后端参数与查询 → 数据库验证 → 前端联调
→ 正常／异常／空结果验证 → 变更说明
```

遵守仓库测试治理：实现与测试不得由同一上下文自我认证，验收标准必须先存在并由人确认。

### 实战 B：一次性环境部署与恢复演练

只在本地或明确授权的测试环境完成：

1. 检查非敏感配置和服务依赖；
2. 构建并启动前后端；
3. 验证静态入口、健康检查和一个真实业务接口；
4. 停止后端并定位故障，再恢复；
5. 创建 MySQL 备份，在一次性测试库验证恢复；
6. 使用前端备份镜像完成一次回滚；
7. 输出操作记录、观察证据、未验证项和恢复边界。

**不以“容器显示 running”作为完整验收，不以“生成了备份文件”作为可恢复证明。**

## 八、当前范围之外

在基础链路、测试和部署恢复验收通过前，暂不主动扩张到：

- Kubernetes、服务网格和微服务拆分；
- JVM 深度调优与复杂性能剖析；
- Spring Security 全家桶替换现有鉴权；
- 分布式事务框架和更多中间件；
- 与当前任务无关的新部署平台。

这些不是永远不学，而是避免同时加载过多工作记忆，让当前项目的核心闭环先变得可解释、可操作、可恢复。
