登录注册与 JWT

本课收获：能完整讲出你的密码如何变成一枚 token、又如何被验回来——以及三处安全设计（BCrypt、同文案、HttpOnly）各自挡住了什么攻击。这是面试必问区。

承接 第 1 课 · 一次请求的完整旅程。本课主角：POST /mall/auth/login。

密码明文 ──→ ① BCrypt 校验 ──→ ② JWT 签发 ──→ ③ 写入 HttpOnly Cookie
                                                             ↑
数据库比对哈希                                     ④ 之后每次请求：拦截器验签 → UserContext

1第一站：密码的存与验——BCrypt

注册时密码永远不明文入库。AuthServiceImpl.java:40：

// 注册：密码经 BCrypt 散列后才落库
user.setPassword(passwordEncoder.encode(req.getPassword()));

backend/src/main/java/com/fullstackmall/shop/user/service/impl/AuthServiceImpl.java:38-44

登录时也不是"解密比对"——BCrypt 是单向算法，不可逆。它用一种叫"盐"（salt）的随机佐料把密码搅成哈希，登录时 matches(明文, 库中哈希) 在算法内部重演搅拌过程，看结果是否一致（AuthServiceImpl.java:53）。

面试点：BCrypt 自带盐，同一密码每次哈希结果都不同，彩虹表（预计算哈希对照表）直接失效；且它故意设计得很"慢"，拖慢攻击者暴力破解的速度。泄露数据库也泄露不了可逆的密码。
第二个安全设计：AuthServiceImpl.java:52-54——用户不存在和密码错误返回同文案。否则攻击者拿"用户不存在"和"密码错误"两种响应的差异，就能逐个试探哪些账号已注册（账号枚举）。

2第二站：JWT 签发——一枚自包含的凭证

校验通过后，Controller 调 JwtService.sign(...) 造 token（JwtService.java:33-43）：

return Jwts.builder()
        .subject(String.valueOf(userId))     // 主题：谁
        .claim("username", username)         // 自定义行李
        .claim("role", role)                 // 角色也装进去（Admin 校验要用）
        .issuedAt(Date.from(now))            // 签发时间
        .expiration(Date.from(now.plus(expireHours, ...)))  // 过期时间
        .signWith(key)                       // 用密钥签名（HS256）
        .compact();

backend/src/main/java/com/fullstackmall/shop/user/service/JwtService.java:33-43

JWT 本质是一张"签了名的 JSON 名片"，分三段：头部（算法声明）· 载荷（上面的 userId/username/role/时间）· 签名。关键认知：载荷只是 Base64 编码，没有加密——任何人解开都能看到里面写了什么；签名保证的是"没人能篡改它"。所以 JWT 里绝不能放密码等敏感信息。

边界纪律（面试加分句）：JwtService 的类注释写明"只做凭证换算，不碰数据库；解析失败原样抛异常，由 AuthInterceptor 翻译成 401——此处不消化异常"。一个类只干一件事，错误的翻译权归调用方。

3第三站：写入 Cookie——三个属性的攻防

ResponseCookie cookie = ResponseCookie.from(cookieName, token)
        .httpOnly(true)      // JS 读不到 → 防 XSS 偷凭证
        .sameSite("Lax")     // 跨站请求默认不带 → 防 CSRF
        .path("/api")        // 只随 API 请求发送，缩小暴露面
        .maxAge(maxAgeSeconds)
        .build();

backend/src/main/java/com/fullstackmall/shop/user/controller/AuthController.java:69-77

为什么 logout 也要服务端来做？HttpOnly 意味着前端 JS 删不掉这枚 Cookie（这正是它的安全价值）。所以 logout 由服务端"原名单发一枚 maxAge=0 的同名 Cookie"把它顶掉（AuthController.java:57-62）。安全设计的代价，由服务端兜回来。

4回程：每次请求如何验回来

第 1 课讲过：拦截器从 Cookie 取 token → jwtService.parse(token) 验签名+查过期 → 装进 UserContext。两个细节值得再看：

① 验签失败（过期/篡改/格式错）统一翻译成"未登录"，不区分原因——不向外泄 JWT 细节（AuthInterceptor.java:35-38）。

② UserContext 提供两个 API（UserContext.java:22-33）：get() 可能返回 null（匿名路径要自行判空）；getRequired() 直接抛 401（受保护路径专用，省掉每个 Controller 手写判空）。

530 秒面试版（背下来）

"密码用 BCrypt 单向散列入库，自带盐、故意慢，抗彩虹表抗爆破；登录时'用户不存在'和'密码错误'同文案，防账号枚举。校验通过后签发 JWT——载荷装 userId/username/role，Base64 不加密所以不放敏感信息，签名防篡改。token 写进 HttpOnly Cookie，JS 读不到防 XSS，SameSite=Lax 防 CSRF。之后每次请求拦截器验签装 ThreadLocal，验签失败统一 401 不外泄原因；请求结束必须 clear，因为 Tomcat 线程复用。"

自检测验

先在心里作答，再点开答案。

1. 登录接口为什么把"用户不存在"和"密码错误"设计成同文案？

  • A · 防攻击者拿响应差异试探账号是否已经注册
  • B · 减少响应内容长度从而提升接口传输性能
  • C · 便于前端统一处理而无需区分两种错误
  • D · 避免数据库重复查询造成连接池压力
查看答案与解析

A。AuthServiceImpl.java:52 注释直说"防账号枚举"。如果两种错误文案不同，攻击者注册前先拿用户名打一遍登录接口，"用户不存在"的就是可攻击目标。B/C/D 都是顺带效果或臆想，不是设计动机。

2. Cookie 的 HttpOnly 属性挡住的是哪种攻击？

  • A · 前端 JS 脚本读取凭证，配合 XSS 完成窃取
  • B · 明文传输被嗅探，凭证在链路上被直接截获
  • C · 跨站请求伪造，诱导浏览器带 Cookie 发起操作
  • D · 恶意网站通过同源策略越权读取响应内容
查看答案与解析

A。HttpOnly = 浏览器禁止 document.cookie 读取，XSS 注入的脚本偷不走凭证。B 是 HTTPS 要解决的问题，C 是 SameSite 要解决的问题（本项目配 Lax），D 说的是 CORS。四个属性各司其职，别张冠李戴。

3. JWT 的签名（signature）究竟保证了什么？

  • A · 令牌内容自签发后没有被任何人篡改过
  • B · 令牌载荷已被加密，他人无法读取其中数据
  • C · 令牌可在任意多个不同域名间共享会话
  • D · 服务端可以随时吊销这枚令牌的生效资格
查看答案与解析

A。签名 = 用密钥对头部+载荷做 HMAC，改一个字节验签就失败。B 错——载荷只是 Base64 编码，人人可读，所以不放密码；C 与签名无关；D 恰恰相反——JWT 无状态的好处是可水平扩展，代价就是服务端没法主动吊销，只能等它过期（本项目 expire-hours 到期自然失效）。
