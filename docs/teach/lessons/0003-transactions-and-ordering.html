事务与下单

本课收获：能讲清"下单"这个动作为什么必须是一个不可分割的事务，以及三处并发防线（条件扣库存、状态条件迁移、订单号 uk 重试）分别挡住了什么。这是面试追问率最高的一课。

承接 第 2 课 · 登录注册与 JWT。本课主角：POST /mall/orders，教材 order/service/impl/OrderServiceImpl.java。

0一个思想实验：下单不能只做一半

假设下单分四步：①扣库存 ②建订单 ③写订单明细 ④建支付单。如果第 ② 步时数据库挂了，会发生什么？没有保护的话：库存扣了，订单没有——货凭空少了，用户什么都没买到。这就是"只做了一半"。

事务（Transaction）就是给这一串操作套上的"要么全成、要么全不算"的契约。Spring 里只需一个注解（OrderServiceImpl.java:108-110）：

@Override
@Transactional
public OrderDTO create(CreateOrderRequest req) { ... }

backend/src/main/java/com/fullstackmall/shop/order/service/impl/OrderServiceImpl.java:108-110

方法内任何一处抛出异常，数据库自动把已执行的全部写入撤销（回滚）；全部顺利才落账（提交）。这就是事务的"原子性"——下单是不可分割的最小工作单元。

注意：本项目的业务异常 BusinessException 也是 RuntimeException 子类，默认触发回滚。所以 Service 里放心抛，写了一半的脏数据不会留库。

cartCreate(userId, req):

2并发防线一：条件 UPDATE 扣库存

两人同时买最后 1 件，怎么保证只有一人成功？关键在一条 SQL（OrderServiceImpl.java:218-227）：

// UPDATE product_item
//   SET stock = stock - 1, version = version + 1
//   WHERE id = ? AND stock >= 1        ← 条件在 WHERE 里
int rows = productItemMapper.update(null, Wrappers.<ProductItem>update()
        .setSql("stock = stock - " + quantity + ", version = version + 1")
        .eq("id", itemId)
        .ge("stock", quantity));
if (rows == 0) {
    throw new BusinessException(ResultCode.STOCK_NOT_ENOUGH);  // 整体回滚
}

backend/src/main/java/com/fullstackmall/shop/order/service/impl/OrderServiceImpl.java:218-227

MySQL 执行 UPDATE 时会给该行上锁，两个请求排队执行：第一人把 1 改成 0，第二人的 WHERE stock >= 1 已经匹配不到任何行——影响行数 0——直接抛异常回滚。"影响行数"就是这次扣减是否成立的裁判。这就是"乐观"以外的"条件更新"防线：不靠锁等待靠条件断言，行数即真相。

3并发防线二：状态条件迁移

取消订单、发货、确认收货都要改状态。裸写法是"查出来判断状态再 update"，两个并发请求会同时通过判断。本项目统一走条件迁移（OrderServiceImpl.java:462-471）：

// UPDATE orders SET status = 'CANCELLED'
//   WHERE id = ? AND status = 'PENDING_PAYMENT'   ← 旧状态写进 WHERE
int rows = orderMapper.update(null, Wrappers.<Order>update()
        .set("status", to.name())
        .eq("id", orderId)
        .in("status", fromNames));
if (rows == 0) throw new BusinessException(ResultCode.ORDER_STATE_ILLEGAL);

backend/src/main/java/com/fullstackmall/shop/order/service/impl/OrderServiceImpl.java:462-471

重复点"确认收货"、并发点"取消"——第二次执行时旧状态已变，WHERE 命中 0 行，被拒。数据库行锁保证同一时刻只有一个迁移能赢。读-改-写三步合成一条 UPDATE，中间没有缝隙可钻。

4并发防线三：订单号唯一键 + 重试

订单号 = M + 时间戳到秒 + 4位随机（OrderNoGenerator.java:28-31），同一秒最多 1 万个号，理论可能撞车。数据库给 orderNo 建了唯一键（uk），撞了就抛 DuplicateKeyException——Service 捕获换号重试 ≤3 次（OrderServiceImpl.java:261-271）：

for (int attempt = 0; attempt < 3; attempt++) {
    order.setOrderNo(OrderNoGenerator.orderNo());
    try {
        orderMapper.insert(order);
        return order;
    } catch (DuplicateKeyException e) {
        if (attempt == 2) throw e;   // 第三次还撞，真异常，向上抛
    }
}

backend/src/main/java/com/fullstackmall/shop/order/service/impl/OrderServiceImpl.java:261-271

面试点：uk 是数据库层的最终裁判——应用层任何生成器的"不冲突承诺"都可能失效，唯一键兜住最后底线；重试把极低概率的冲突变成透明重试，而不是用户可见的失败。

5两个设计彩蛋：快照铁律与惰性关单

1

快照铁律——订单明细存 JSON，不 join 商品表

下单瞬间把标题/图/成色/规格/品牌/成交价定格进 itemSnapshot（OrderServiceImpl.java:229-250）。半年后商品改价、下架、卖家改名，历史订单展示纹丝不动。订单是法律凭证，商品表是活数据——用活数据渲染凭证，等于允许篡改历史。

2

惰性关单——不用定时任务的取消

订单 15 分钟不支付要取消+还库存。常规做法是起个定时任务每秒扫表；本项目是"查询触发"：你查订单列表/详情时，顺手把已过期的批量关掉（OrderServiceImpl.java:322-326）。没有调度器、没有轮询空转，代价是"过期订单可能晚几分钟才显式关闭"——但没人看它的时候它关没关，根本无所谓。

630 秒面试版（背下来）

"下单是一个 @Transactional 事务：地址和购物车行先做归属校验防越权，然后逐行条件 UPDATE 扣库存——SET stock=stock-1 WHERE stock>=1，影响行数为 0 就说明被抢先或不足，整体回滚；库存 1 的寄卖直购同理。订单状态变更全部走条件迁移，旧状态写进 WHERE，行数守卫让并发重复操作只放行一个。订单号是时间戳+随机数，撞 uk 就换号重试三次。明细和地址都存 JSON 快照，商品后续怎么改都不牵连历史订单。超时关单不做定时任务，查询时惰性触发，还库存同事务完成。"

自检测验

先在心里作答，再点开答案。

1. create 方法标了 @Transactional，执行到一半抛出 BusinessException，数据库会怎样？

  • A · 已执行的写入全部撤销，恢复到方法执行前状态
  • B · 已执行的写入全部保留，仅中断后续语句不再执行
  • C · 事务挂起并等待人工介入，再决定提交还是回滚
  • D · 异常被自动捕获并吞掉，方法返回默认值继续走
查看答案与解析

A。这是事务的原子性：要么全成，要么全不算。BusinessException 是 RuntimeException 子类，默认触发回滚，已扣的库存、已插的草稿行全部撤销。B 是最危险的误解（只做一半）；C/D 描述的不是 Spring 声明式事务的行为。

2. 条件 UPDATE（WHERE stock >= q）执行后影响行数为 0，意味着什么？

  • A · 库存不足或已被他人抢先，本次下单整体回滚
  • B · 数据库连接已中断，需要重试该语句才能继续
  • C · 商品已下架，应立即删除该商品的全部数据
  • D · 查询条件书写有误，属于必须修复的程序缺陷
查看答案与解析

A。行数 0 只有两个合法含义：当前库存 < q（不足），或并发下已被别人扣走（抢先）。两种情况对调用方等价：库存不够，抛 STOCK_NOT_ENOUGH 回滚。B/C/D 都是把"业务结果"误读为"系统故障"。这正是行数守卫的思维方式：行数是业务裁判，不是错误信号。

3. 订单明细把标题/图片/价格存成 itemSnapshot JSON，根本原因是什么？

  • A · 商品日后改价或下架，历史订单展示不被牵连
  • B · JSON 查询速度远快于关联商品表做 join 查询
  • C · 减少数据库表数量从而节约磁盘存储的开销
  • D · 前端可直接解析渲染快照而无需做字段转换
查看答案与解析

A。订单是凭证，凭证必须定格成交瞬间的事实。商品表是活数据——半年后改价、改名、下架都会发生。若订单展示靠 join 商品表，历史订单就会"跟着变"，等于默许篡改凭证。B 恰恰相反（join 通常更快）；C/D 可能是顺带效果，但都不是设计动机。
