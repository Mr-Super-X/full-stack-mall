支付与幂等

本课收获：能讲清"支付宝回调来了"之后后端如何证明它是真的、没被动过、且来几次都只生效一次。幂等是分布式系统的面试必考词，本课让它落地。

承接 第 3 课 · 事务与下单。本课主角：POST /mall/payments/fake/notify，教材 payment/service/impl/PaymentServiceImpl.java。

0先理解回调的三个"坏毛病"

支付结果不是前端告诉后端的，而是支付网关异步回调通知的（为什么不信前端？因为前端可以被伪造）。但回调这个信使有三个坏毛病：

① 可能是假的——任何人都能往 /notify 发请求（所以它免登录，登录态管不了服务器）
② 可能被改过——中间人把回调里的金额 9.9 改成 0.01
③ 可能来很多次——网关没收到你的响应就会重发（至少一次投递语义）

notify 方法用八步应对（PaymentServiceImpl.java:84-134）。下面按三道防线讲。

1防线一：验签——证明"你是真的支付宝"

// 1. 验签：回调的可信来源是签名而非登录态
if (!paymentProvider.verifySign(req.getPaymentNo(), req.getAmount(), req.getSign())) {
    log.warn("支付回调验签失败：paymentNo={}", req.getPaymentNo());
    throw new BusinessException(ResultCode.BAD_REQUEST);
}

backend/src/main/java/com/fullstackmall/shop/payment/service/impl/PaymentServiceImpl.java:85-89

原理：商户和网关共享一个密钥。网关把 paymentNo+amount+key 做哈希得到签名 sign 一并回调；后端用同样的算法重算一遍，不一致就是假的。模拟实现用 md5，真实支付宝用 RSA 非对称密钥——思路相同：签名证明来源，而不是登录态（呼应第 1 课：/notify 被排除在 AuthInterceptor 之外，因为它根本不是浏览器请求）。

2防线二：金额校验——证明"你没被改过"

// 5. 金额校验：回调金额必须等于应付（篡改检测）
if (payment.getAmount().compareTo(req.getAmount()) != 0) {
    log.warn("支付回调金额不符：...");
    throw new BusinessException(ResultCode.BAD_REQUEST);
}

backend/src/main/java/com/fullstackmall/shop/payment/service/impl/PaymentServiceImpl.java:104-109

验签防"伪造"，但假设密钥泄露或签名被重放呢？第二关：只信数据库里的应付金额。回调说"付了 0.01"，库里记着 9.9，直接拒。金额是后端自己的账本说了算，回调说了不算。

3防线三：幂等——证明"第几次来都一样"

幂等（idempotent）：同一个操作执行一次和执行 N 次，效果完全相同。网关重发三次"支付成功"，绝不能给订单加三次销量。本项目用三层结构实现：

1

第一层：已成功的直接短路

// 3. 重复回调幂等：已 SUCCESS 直接返回，不重复推进
if (payment.getStatus() == PaymentStatus.SUCCESS) {
    return Map.of("success", true, "message", "重复回调已忽略");
}

PaymentServiceImpl.java:96-99

2

第二层：状态机只许单向

// 4. 状态机单向：仅 CREATED/PAYING 可迁移
if (payment.getStatus() != CREATED && payment.getStatus() != PAYING) {
    throw new BusinessException(ResultCode.PAYMENT_STATE_ILLEGAL);
}
// 8. 条件迁移：WHERE status IN (CREATED, PAYING)
migratePaymentStatus(payment.getId(), SUCCESS, CREATED, PAYING);

PaymentServiceImpl.java:100-103, 127

状态机：CREATED → PAYING → SUCCESS（或 FAILED）。没有回头路，没有跳跃。条件迁移（第 3 课范式）保证并发下只有一条回调能把状态推过去。

3

第三层：行数裁判决定"要不要做副作用"

// 订单 PAID 条件迁移：行数 1 = 本次回调真正推进；0 = 并发/重复已推进
private boolean migrateOrderPaid(Long orderId) {
    int rows = orderMapper.update(... .eq("status", "PENDING_PAYMENT"));
    return rows == 1;
}
// 调用处：只有真正推进的那次回调才累加销量
if (migrateOrderPaid(order.getId())) {
    accrueSales(order.getId());
    markConsignmentsSold(order.getId());
}

PaymentServiceImpl.java:176-183, 127-132

这是全课最精妙的一笔：销量累加不是无条件执行，而是"我这次真的把订单状态推过去了"才执行。三条并发回调只有一个能命中 WHERE 迁成 PAID（行数 1），只有它配累销量；另外两条撞行数 0，安静返回成功。对网关来说三次都得到 success（所以网关不再重发），对系统来说副作用只发生一次。

极端场景：用户拖到最后 1 秒支付，钱扣了，但订单已被惰性关单。这时钱货两空（"资金黑洞"）。本项目的选择：记 error 日志、拒绝推进、把 TODO 和设计方案（§4.5 钱的两条线）留在代码里，而不是假装问题不存在。面试时主动讲这个边界，比背八步更能体现工程判断力。

5FakeProvider：用假网关教真知识

没有真实支付宝，怎么闭环？项目写了一个模拟网关：收银台页面展示金额（PaymentController.java:55-100），点"完成支付"就带签名 POST /notify——数据结构、验签链路、异步回调时序与真实支付宝同款。换成真实渠道只需实现 PaymentProvider 接口换一家实现。这就是"抽象隔离变化"的最小教学样本。

630 秒面试版（背下来）

"支付回调免登录但绝不裸奔：第一道验签证明来源是网关（共享密钥重算哈希），第二道金额校验只信库里的应付金额防篡改，第三道幂等分三层——已 SUCCESS 直接短路、状态机单向条件迁移、最后用行数裁判决定副作用：只有真正推进订单到 PAID 的那次回调才累销量，重复回调返回成功但不再产生任何写操作。另外订单已关但钱到了这种资金黑洞，我们记日志拒绝推进并留了退款流水的 TODO——边界问题显式处理而不是吞掉。"

自检测验

先在心里作答，再点开答案。

1. 支付回调为什么靠验签而不是登录态做身份认证？

  • A · 调用方是网关服务器，浏览器那套登录态管不到它
  • B · 签名比 Cookie 校验速度快，可以撑起更高回调吞吐
  • C · 登录态经网关转发时容易意外丢失，无法找回
  • D · 用户可能伪造请求，所以必须用非对称加密验签
查看答案与解析

A。回调是服务器对服务器的调用，发起方不是用户的浏览器，自然没有用户的 Cookie（第 1 课讲过它被排除在 AuthInterceptor 之外）。身份的证明方式换成"共享密钥算签名"。D 的前半句对（要防伪造）但验签 symmetric md5 / 非对称 RSA 都行，"必须非对称"不成立；B/C 不是设计动机。

2. 同一笔支付的成功回调到达三次，本系统会怎样？

  • A · 第一次推进状态累销量，后两次返回成功不再写库
  • B · 每次都累加销量，所以去重必须依赖网关侧完成
  • C · 第二次起抛异常报错，让网关持续重试直到人工
  • D · 三条回调生成三张订单，分别进入并发发货流程
查看答案与解析

A。三层幂等叠加的效果：第一次回调把支付单迁成 SUCCESS、订单条件迁成 PAID（行数 1）→ 累销量；第二三次来，要么命中"已 SUCCESS 直接短路"，要么订单迁移行数 0 跳过副作用。三次都返回 success（网关满意不再重发），系统只写一次。B/D 正是幂等要防的事故；C 会让网关无限重试打爆服务。

3. 回调金额与数据库应付金额不一致时，正确处置是？

  • A · 判为可疑请求拒绝处理，并记录警告日志追踪
  • B · 以回调金额为准，同步更新支付单订单金额
  • C · 取两金额中较小值，向用户收取部分款项
  • D · 视为网关优惠活动，自动接受差额完成结算
查看答案与解析

A。金额只信自己的账（payment.getAmount()），回调金额不符 = 篡改或异常，拒绝 + 记日志。B 等于把账目主权交给外部；C/D 是玩笑式的错误选项——真实系统里任何"按回调金额改账"的想法都是资金漏洞。
