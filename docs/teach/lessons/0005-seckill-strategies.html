秒杀三策略对照

本课收获：同一套下单接口背后的三种扣库存实现——数据库乐观锁、悲观锁、Redis+MQ 异步——各自原理、代价、以及压测数据怎么支撑选型。这是本项目最硬的一道面试题，也是"你项目里最难的技术点"的标准答案。

承接 第 4 课 · 支付与幂等。本课主角：POST /mall/seckill/{id}/orders。

0先定义问题：秒杀难在哪

一万个人抢同一件商品的 10 件库存。难在三点：

① 热点行——所有请求 UPDATE 同一行，数据库行锁变成串行排队
② 超卖即资损——卖出 11 件 = 平台赔 1 件 + 客诉，正确性高于一切
③ 突发流量——0 点整请求洪峰，同步落库的事务越长排队越惨

1一个开关，三种实现

三策略不是三个接口，而是同一个 placeOrder 契约下的三个实现，靠配置切换（SeckillProperties.java:15，环境变量 SECKILL_STRATEGY），分派就在 Service 里（SeckillServiceImpl.java:280-288）：

// 5. redis 策略：Lua 预扣 + 受理落库 + 提交后发 MQ（受理即返）

    default -> deductStock(activityId);   // OPTIMISTIC

对照实验的公平性怎么保证？——前后置步骤（查活动/惰性推进/挂载校验/限购/建单）完全一致，只有"扣库存"这一步的实现不同。这是压测数字可比的前提（建单三步还抽了共用 SeckillOrderAssembler）。

2策略一 · OPTIMISTIC：条件更新（第 3 课范式的复用）

// UPDATE seckill_activity SET sold_count = sold_count + 1
//   WHERE id = ? AND sold_count < seckill_stock   ← 行数 0 = 抢完

就是第 3 课"条件 UPDATE + 行数裁判"。优点：实现简单、无锁等待；缺点：大量并发下所有人挤同一行，UPDATE 排队，响应时延随并发线性涨。它是默认策略（4a 形态），也是其余两策略的对照基线。

3策略二 · PESSIMISTIC：FOR UPDATE 行锁（对照组）

// DbPessimisticDeductor.java:32-49
SeckillActivity locked = seckillActivityMapper.selectForUpdate(activityId);  // 锁行
if (sold >= locked.getSeckillStock()) throw ...SOLD_OUT;
// 锁内再条件更新双保险
int rows = seckillActivityMapper.update(... .ge("sold_count", sold));

backend/src/main/java/com/fullstackmall/shop/seckill/service/DbPessimisticDeductor.java:32-49

先 SELECT ... FOR UPDATE 把行锁住，别人排队等我提交。语义最直白，但吞吐上限被行锁串行化锁死，且锁等待会放大拐点。类注释写明它是"压测/教学用途，故意保留锁等待/死锁风险"——作为对照组存在的意义，是让压测曲线替你说出"悲观锁在这种热点场景为什么不行"。

4策略三 · REDIS：Lua 预扣 + MQ 异步出单（4b 主形态）

1

关口：一段 Lua 脚本把"判库存+占位+扣减"焊成原子操作

local stock = tonumber(redis.call('GET', KEYS[1]) or -1)
if stock < 0 then return -1 end        -- 关口缺失
if stock == 0 then return 0 end        -- 抢完
if redis.call('SET', KEYS[2], ARGV[1], 'NX', 'EX', 900) == false
   then return -2 end                    -- 已占位（限购）
redis.call('DECR', KEYS[1])              -- 扣 1
return 1

RedisStockDeductor.java:38-51（三分支脚本：1 成功 / 0 抢完 / -1 缺失 / -2 已占位）

Redis 执行 Lua 脚本时不会插入其他命令——判库存、占位（一人一场，TTL 900s 对齐订单超时）、扣减三步物理上不可分割，超卖在 Redis 层不可能发生。DB 从此退居"真相源"：关口 key 丢了用 (seckill_stock - sold_count) 自愈重建。

2

受理即返：同步路径里最贵的一步被搬出请求线程

// placeOrderRedis 时序（SeckillServiceImpl.java:415-448）：
1. Lua 预扣                      ← 毫秒级
2. 地址校验 + 受理记录落库        ← 小事务（ACCEPTED 受理表）
3. afterCommit 发 MQ             ← 事务提交后才发
4. return (orderNo, null)        ← 用户立刻拿到"排队凭证"，paymentNo 为空

SeckillServiceImpl.java:415-448

对比：OPTIMISTIC/PESSIMISTIC 是七步事务同步建单（返回 orderNo + paymentNo，用户直接在收银台）；REDIS 是受理即返（只返回 orderNo，paymentNo 为 null），前端拿 orderNo 轮询 /mall/seckill/orders/{orderNo}，MQ 消费者异步建单成功后才拿到 paymentNo 进收银台。请求线程不等落库事务，时延与落库压力解耦。

3

一致性细节：每个失败路径都有补偿

// 事务段失败 → 回补 Redis（SeckillServiceImpl.java:429-432）
} catch (RuntimeException e) {

    throw e;

// MQ 发送失败 → 受理置 FAILED + Redis 回补（:451-462）
// 消费失败 3 次 → 进 DLX，DlxMonitor 自动回补（受理 FAILED + 关口复原）
// 重复消费 → 消费者按 orderNo 幂等查重，订单恒 1
关键取舍：Redis 宕机时拒绝服务（503 + 40005），不降级回 DB——降级会让 Redis 和 DB 两本账真相分裂，宁可拒绝不可超卖。这就是"最终一致，宁可少卖不超卖"（超卖=资损+客诉，少卖=损失一次成交，代价不对称）。

630 秒面试版（背下来）

"秒杀我们用同一接口做了三种扣库存实现，一个配置开关切换跑对照压测。乐观锁是条件 UPDATE 行数守卫，简单但高并发挤热点行；悲观锁 FOR UPDATE 锁行，吞吐被串行化锁死，留作教学对照组；最终选型 Redis Lua 预扣 + RabbitMQ 异步出单——Lua 把判库存、一人一场占位、扣减焊成原子操作，超卖在 Redis 层物理不可能；DB 退为真相源支持自愈重建。下单线程只做 Lua 预扣 + 受理表小事务，提交后 afterCommit 发 MQ 异步建单，受理即返，前端轮询拿 paymentNo。每个失败路径都有补偿：事务回滚/MQ 失败补 Redis INCR，消费失败进 DLX 由监控器回补，重复消费靠 orderNo 幂等。Redis 宕机我们选择 503 拒绝而不是降级 DB——宁可少卖不超卖。JMeter 五档并发实测：redis 趟 T=500 时延 954ms vs 同步方案 1345/1658ms，15 组压测超卖少卖全零。"

自检测验

先在心里作答，再点开答案。

1. 为什么 Lua 脚本能从物理上杜绝超卖？

  • A · 脚本执行中间不会插入任何其他客户端命令
  • B · Redis 把库存 key 标记为只读禁止外部修改
  • C · 脚本运行前会自动对库存 key 加分布式锁
  • D · Redis 单线程模型执行期间拒绝一切连接
查看答案与解析

A。Redis 保证同一时刻只有一个 Lua 脚本在执行，脚本内多条命令之间不会有其他命令插队——判库存、占位、DECR 三步不可分割，自然没有"都看到 stock=1"的竞态。C 的"分布式锁"是多余的发明（Redlock 正是本项目明确不做的，见取舍声明）；D 错在"拒绝连接"——其他客户端照常连接，只是命令排队。

2. MQ 消息放在 afterCommit（事务提交后）发送，防的是什么？

  • A · 消息已发出但事务随后回滚造成的幽灵订单
  • B · MQ broker 宕机导致消息在队列中永久丢失
  • C · 消费者处理太快早于数据库事务提交完成
  • D · 网络抖动导致消息到达顺序错乱被重复消费
查看答案与解析

A。事务内直接发 MQ 的风险：消息已投递、消费者正准备建单，本地事务却回滚了——消费者看到一条"并不存在"的下单指令（幽灵订单）。afterCommit 保证消息只在事务铁定提交后才发出。B/D 是别的问题（发送失败有 INCR 补偿、重复消费有 orderNo 幂等查重）；C 因果关系反了。

3. Redis 宕机时选择 503 拒绝而非降级查 DB，核心理由是？

  • A · 降级会让 Redis 与数据库两本账真相分裂
  • B · 数据库没有库存字段无法承担扣减职责
  • C · 503 响应更快从而提升接口吞吐指标表现
  • D · 降级需要反向同步 Redis 改造成本过高
查看答案与解析

A。RedisStockDeductor 类注释的原话（取舍声明）："降级会让双写真相分裂，宁可拒绝不可超卖。"Redis 已扣了 3 件、DB 不知道，降级走 DB 又会按它的 sold_count 放行——两本账对不上，超卖风险反而变大。B 是事实错误（DB 当然是真相源）；C 把拒绝服务说成性能优化；D 的"成本"不是核心——核心是不可超卖的正确性红线。
