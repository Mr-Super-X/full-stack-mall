寄卖与结算闭环

本课收获：讲清一个闲置如何变成在售商品、成交后平台怎么按比例与卖家分钱。你会看到前 5 课所有范式（状态条件迁移、事务、幂等、行数裁判）在一条完整业务链上协同工作——这是"全局观"的一课。

承接 第 5 课 · 秒杀三策略对照。

0两条线：货在走，钱在等

寄卖（C2C）业务的本质：货的所有权在卖家，平台只撮合与结算。所以系统里永远有两条并行的线：

货流线：寄卖单状态机 SUBMITTED → PRICED → LISTED → SOLD → SETTLED（↘ REJECTED）
资金线：确认收货时生成 Payout（PENDING）→ 平台确认（CONFIRMED）→ 打款（PAID）
          规则：收货才结算——买家没确认收到货之前，钱不进入打款流程

ConsignmentStatus.java:4-6（"钱的两条线"设计见设计文档 §4.5）

1货流五步

1

① 提交（SUBMITTED）

卖家提交闲置：标题/描述/成色/期望价/类目/图片。ConsignmentServiceImpl.submit 落库即入审核池。

2

② 平台审核定价（SUBMITTED → PRICED / REJECTED）

review（ConsignmentServiceImpl.java:164-186）：管理员定一个平台售价 + 佣金率。驳回必须给原因。条件迁移——重复审核第二次命中 0 行被拒。

3

③ 卖家接受定价：铸造商品（PRICED → LISTED）

全课最重的一个事务（ConsignmentServiceImpl.java:97-140）：

@Transactional
public ConsignmentDTO accept(Long id) {
    // 原子迁移占位：并发下只有一个请求能把 PRICED 改为 LISTED
    migrateStatus(id, ConsignmentStatus.LISTED, ConsignmentStatus.PRICED);
    // 1. 铸造商品（寄卖身份 + 卖家归属）  2. 铸造 SKU（stock 恒 1）
    // 3. 复制图片                         4. 回写寄卖单状态 + 铸造产物 id
    // 四写任一失败整体回滚，不留半截商品
}

"先迁移占位、再干活"的顺序：并发双击"接受定价"时，只有第一个请求能占位成功，第二个在第一步就撞行数 0 回滚——天然防重复铸造。四张表（寄卖单/商品/SKU/图片）要么全部出现，要么全部不出现。

4

④ 售出（LISTED → SOLD）

发生在第 4 课的支付回调里（PaymentServiceImpl.markConsignmentsSold）：订单转 PAID 时，寄卖明细对应的寄卖单条件迁移 SOLD。行数 0 只记 debug——幂等容忍，不影响支付主流程。

5

⑤ 结算归档（SOLD → SETTLED）

发生在下面资金线第三步打款时联动完成。

2资金线三步：Payout 审批

// PayoutServiceImpl.java:62-87 —— 每步都是条件迁移（第 3 课范式）
confirm(id):  PENDING   → CONFIRMED   // 财务核对金额
pay(id):      CONFIRMED → PAID
              // 同事务联动寄卖单 SOLD → SETTLED（PayoutServiceImpl.java:74-84）
              // 打款与归档任一失败整体回滚，不留中间态

backend/src/main/java/com/fullstackmall/shop/payout/service/impl/PayoutServiceImpl.java:60-87

三步而非一步的意义：职责分离。系统算出"该给卖家多少钱"（CONFIRM 核对）与"真的把钱打出去"（PAY）是两个角色的事；状态机强制必须按序走完，跳步即撞行数 0。

3佣金从哪来：确认收货那一刻

// OrderServiceImpl.confirm（条件迁移 SHIPPED→COMPLETED）之后：
for (OrderItem line : lines) {
    if (line.getSellerId() == null) continue;        // 自营明细无结算
    // 幂等：uk(order_item_id) 已存在则跳过
    Long exists = payoutMapper.selectCount(... .eq(Payout::getOrderItemId, line.getId()));
    if (exists > 0) continue;
    // 佣金率回联寄卖单（经 productItem → listed_product_id 链路）
    BigDecimal commission = gross.multiply(rate)
            .divide(BigDecimal.valueOf(100), 2, RoundingMode.HALF_UP);
    BigDecimal sellerAmount = gross.subtract(commission);   // 卖家实收 = 成交额 - 佣金
    payoutMapper.insert(payout);   // PENDING
}

backend/src/main/java/com/fullstackmall/shop/order/service/impl/OrderServiceImpl.java:402-435

三个细节：① 佣金率不存订单——订单快照存的是商品信息，费率要回联寄卖单取（审核时定下的）；② HALF_UP 两位小数，钱的计算必须显式指定舍入模式，否则不同 JDK 默认舍入可能不同；③ uk(order_item_id) 让重复确认收货不会产生第二张结算单——幂等又一次兜底。

4串起来：一件闲置的一生

时刻动作状态变化用到了哪课的知识
T1卖家提交闲置— → SUBMITTED第 1 课 鉴权链路
T2平台审核定价SUBMITTED → PRICED第 3 课 条件迁移
T3卖家接受定价PRICED → LISTED + 铸造商品第 3 课 事务原子性 + 占位防并发
T4买家支付成功寄卖单 LISTED → SOLD第 4 课 验签 + 幂等回调
T5买家确认收货订单 → COMPLETED，生成 Payout PENDING第 3 课 行数裁判 + uk 幂等
T6平台确认并打款Payout → PAID，寄卖单 → SETTLED第 3 课 条件迁移 + 同事务联动

六步跨越了 auth/consignment/product/payment/order/payout 六个域——每个域只做自己的事，靠状态机和事件联动串成闭环。这就是"按业务分包"架构的价值：任何一步的改动都被关在自己的域里。

530 秒面试版（背下来）

"寄卖是 C2C：货是卖家的，平台撮合+结算，所以系统里有两条线。货流线五个状态 SUBMITTED→PRICED→LISTED→SOLD→SETTLED：卖家提交、平台审核定价、卖家接受定价时一个事务铸造商品三表——先条件迁移占位再干活，并发双击只有一人成功，四写任一失败整体回滚不留半截商品。买家支付成功回调把寄卖单推进 SOLD，买家确认收货时按 uk(order_item_id) 幂等生成 Payout——佣金率回联寄卖单取，HALF_UP 两位小数，卖家实收等于成交额减佣金。资金线三步审批 PENDING→CONFIRMED→PAID，打款和寄卖单 SETTLED 归档在同一个事务里，不留中间态。"

自检测验

先在心里作答，再点开答案。

1. accept 里"先条件迁移 PRICED→LISTED、再铸造商品"的顺序为什么这样设计？

  • A · 并发双击只有一个能占位成功，另一个第一步就回滚
  • B · 先迁移让审核队列页面更快显示商品已上架状态
  • C · 状态字段建有索引可以提升后续铸造语句的速度
  • D · 防止管理员在铸造期间把寄卖单改回 PRICED 状态
查看答案与解析

A。"占位先行"把并发竞争收敛到第一步：两个请求同时到，只有一个的 UPDATE 能命中 WHERE status=PRICED 迁成 LISTED，另一个行数 0 直接抛异常回滚——后面三张表的写入根本不会发生。如果先铸造再迁移，两人都会造出商品，兜底就难做了。B/C/D 都不是这个顺序的真实动机。

2. Payout 表给 order_item_id 建唯一键（uk），目的是什么？

  • A · 重复确认收货不会生成两张结算单导致重复打款
  • B · 加快按订单明细反查结算单时的检索速度表现
  • C · 防止卖家篡改结算金额字段进行欺诈的行为
  • D · 让数据库为结算单自动生成递增的主键编号
查看答案与解析

A。确认收货可能因网络重试/用户双击发生多次。应用层虽有"先查数再插入"的守卫，但查与插之间有缝隙；uk 让数据库兜底——第二条 INSERT 直接撞键失败。打款类数据必须数据库级幂等，不能信应用层的"先查一下"。B 是索引的顺带效果不是目的；C/D 与 uk 语义无关。

3. 打款（Payout→PAID）和寄卖单归档（SOLD→SETTLED）为什么必须在同一事务？

  • A · 防止"钱打了但单没结"或反向的中间态残留
  • B · 管理员连点打款按钮时依靠事务实现防重点击
  • C · 缩短审批页面的加载时间优化管理员体验
  • D · 卖家同时提现多笔时避免连接池被耗尽掉
查看答案与解析

A。类注释原话："打款与寄卖单 SETTLED 联动同在一个 @Transactional——任一失败整体回滚，不留中间态。"两半动作分属两条线（资金/货流），但对账时它们必须同时成立；拆成两个事务，中间崩溃就会留下"钱已打但寄卖单还挂着 SOLD"的烂账。B 靠条件迁移防（行数 0），不是靠事务；C/D 与本设计无关。
