full-stack-mall 后端课 · Lesson 7 · 支线 · 构建之路 ①

数据库从零设计：15 张表是怎么想出来的

本课收获：拿到 init.sql 这 379 行，你能讲清每一张表为什么存在、为什么长这样——分域、公共骨架、唯一键护栏、时间快照、种子数据五步设计法；并且敢对脚本本身挑刺。SQL 不是"写出来的"，是从设计文档里"长出来的"。

承接 第 6 课 · 寄卖与结算闭环。主线六课讲的是"系统在运行时怎么转"，这条支线讲"系统是怎么从零被建出来的"——第 7 课先看地基（数据库），第 8 课看楼层（后端五步闭环）。

0先读出生证明：文件头三行

打开 backend/sql/init.sql，前 4 行注释就是整套数据库的"出生证明"：

-- 转卖商城数据库初始化：全部 MVP 核心表 + 双货源种子数据（2026-11-06 重构）
-- 设计基准：docs/superpowers/specs/2026-11-06-resale-mall-design.md
-- 幂等可重跑：DROP + CREATE。无物理外键（逻辑外键）。
-- 用户种子密码为 BCrypt 哈希（admin123 / seller123 / buyer123 ...）

sql/init.sql:1-4

三行注释藏着三个关键事实：

① 设计先行——表结构不是边写代码边凑的，它有一份设计文档做基准（docs/superpowers/specs/2026-11-06-resale-mall-design.md）。DDL（数据定义语言）是设计的"编译产物"。
② 声明幂等——作者的目标是"重复执行不报错、结果一致"。这是工程态度，但它只是目标声明，§5 你会看到它没完全做到。
③ 无物理外键——表之间不靠数据库的 FOREIGN KEY 强绑，关系由应用层维护。这是面试必问题，§3 专门拆。

怎么学这一课：把 init.sql 放在手边对照着读。每一节我都会给文件行号——你要能自己跳过去验真，不要信我，信文件。

1第一步：从业务域"长"出表

设计表的第一步不是想字段，是分域——把业务拆成几个互不相识的小王国，每个王国管自己的表。init.sql 用注释线把 15 张表分成了 5 个域：

域表（init.sql 行号）管什么
用户域user(25) / address(39)账号、收货地址
商品域product_category(60) / product(74) / product_item(97) / product_image(113) / home_banner(123)类目、商品、规格单件、图片、首页轮播
寄卖域consignment_listing(137)卖家寄卖单与审核流
交易域cart_item(161) / orders(174) / order_item(192) / payment(205) / payout(219)购物车、订单、明细、支付流水、卖家结算
玩法域seckill_activity(235) / seckill_order_acceptance(252)秒杀场次、异步受理登记

注意商品域的三层拆分：product 是"商品"（名字、卖点、归属），product_item 是"规格/单件"（尺码、价格、库存、乐观锁版本号），product_image 是"图"。一件风衣有 S/M/L 三个尺码 = 1 行 product + 3 行 product_item。拆表的标准是"变化频率和归属"：名字描述很少变，库存每单都变——混在一起就会互相锁死。

还有一个细节：orders 表名带 s，因为 ORDER 是 MySQL 保留字（排序关键字），直接起名会语法报错（init.sql:173 有注释）。命名时要给保留字让路。

2第二步：每张表都套同一件"公共骨架"

把 user 表的定义和 product 表的定义并排看，会发现它们共享同一套骨架：

id          BIGINT       NOT NULL AUTO_INCREMENT,   -- 主键：雪花之外的朴素选择
create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
PRIMARY KEY (id),
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT ='用户';

sql/init.sql:25-37（user 表完整定义）

四个约定，逐个有因：

· BIGINT AUTO_INCREMENT：主键用 64 位整数自增。够用、好记、聚簇索引友好——MVP 阶段不上雪花 ID（分布式全局唯一 ID），因为单库足以支撑。
· InnoDB：MySQL 的事务引擎。本项目所有写操作依赖它的行锁与回滚（第 3 课的事务、第 5 课的 FOR UPDATE 都建立在它之上）。
· utf8mb4：完整的 UTF-8（一个 emoji 占 4 字节）。旧编码 utf8 是阉割版，存不了 emoji 也存不了生僻字——新项目一律 utf8mb4。
· update_time ... ON UPDATE CURRENT_TIMESTAMP：行被修改时自动刷新更新时间，应用层不用记得手动维护它。

3第三步：唯一键是业务护栏（本课灵魂）

这是面试最值钱的一节。init.sql 声明"无物理外键（逻辑外键）"，但 15 张表里塞满了 UNIQUE KEY。外键管"关系存在"，唯一键管"业务正确"——本项目把一致性的最后一道防线全部押在唯一键上：

唯一键（行号）防什么事故对应哪课
user.uk_username(36)两个同名校验请求同时通过 → 数据库拒掉第二个第 2 课
address.uk_default_guard(55)并发设默认地址 → 同一用户永远只有一个默认本课 §4
cart_item.uk_user_item(170)同一规格重复加购 → 只能插一行，改数量而非建行—
orders.uk_order_no(187)订单号撞车 → 业务唯一性第 3 课
orders.uk_user_activity(188)秒杀同一人买两单 → 第二个直接撞键失败第 5 课
payment.uk_payment_no(215)支付回调重试 → 同流水号只落库一次第 4 课
payout.uk_order_item(230)重复确认收货 → 绝不生成两张结算单第 6 课

回看主线六课：第 3 课的 uk 重试、第 4 课的三层幂等、第 5 课的一人一单、第 6 课的防重复打款——它们的物理兜底全在这一张表里。应用层做的校验（先查再插）都有缝隙，唯一键没有。这就是"幂等键进表"的含义：把并发正确性从代码搬到数据库。

面试问答模板："为什么不用外键？"——逻辑外键由应用层维护，写入路径集中、可控；物理外键在并发写入时会引入额外的锁与级联检查，高并发下容易成为瓶颈；而业务唯一性（幂等、一人一单）靠唯一键兜底，它不防"关系断掉"，但关系断掉可以靠对账发现，重复打款不能。

4第四步：让表会讲"时间的故事"

两套手法，让数据库回答"当时发生了什么"，而不是只回答"现在是什么"：

① 快照字段（JSON）。下单瞬间把地址和商品定格：

address_snapshot JSON DEFAULT NULL COMMENT '下单时地址快照',
...
item_snapshot JSON NOT NULL COMMENT '标题/图片/成色/尺码快照，定格下单瞬间',

sql/init.sql:181（orders）/ 196（order_item）

买家半年后看订单，收货地址还是当时那个——哪怕他后来改了地址、商品后来下架改名。快照是历史事实的定格，这是交易系统的铁律。

② 状态字段 + 条件迁移。orders.status 从 PENDING_PAYMENT → PAID → SHIPPED（init.sql:179）、consignment_listing.status 七态（150）、payout.status 三态（225）。每个状态字段配一个 WHERE status=旧值 的 UPDATE，行数当裁判（第 3 课的条件迁移）。product_item.version（106 行）则给乐观锁留了版本号，第 5 课的对照组策略用到它。

③ 生成列护栏（彩蛋）。MySQL 没有"部分唯一索引"，没法直接表达"每个用户只能有一个默认地址"。init.sql 第 50 行用了一个技巧：

default_guard BIGINT GENERATED ALWAYS AS (IF(is_default = 1, user_id, NULL)) COMMENT '默认地址唯一护栏（勿手写）',
...
UNIQUE KEY uk_default_guard (default_guard)

sql/init.sql:49-55

生成列是"算出来的列，不能手写"：is_default=1 时它的值等于 user_id，否则是 NULL；唯一索引不约束 NULL，于是"每个 user_id 最多出现一次 1"被数据库强制执行。并发双击"设为默认"？两个请求都想让 user_id 出现第二次——必败一个。这是把业务规则编码进 schema 的高级手法，值得在面试里主动提。

5第五步：种子数据也是工程资产

init.sql 后半部（262-378 行）不是垃圾数据，是三份精心设计的测试资产：

· 相对时间：秒杀种子用 DATE_SUB(NOW(), INTERVAL 1 DAY) 表示"昨天开始"（263-266 行注释原话："绝对日期会过期"）。脚本今天跑、下个月再跑，活动状态依然正确——这是为"可重跑"服务的。
· 递归 CTE 批量造人：500 个压测账号（perf001~perf500）用 6 行递归 CTE 生成（283-290 行），密码共用同一个 BCrypt 哈希（由 PasswordHashPrinter 工具生成并自校验）。手敲 500 行 INSERT 才是反工程。
· 双货源剧本：13 件自营 + 2 件寄卖（Chanel 包、Acne 围巾）+ 各自走完 LISTED 的寄卖单（376-378 行）——种子数据本身演了一出"寄卖全链路"的小品，前端首页一打开就有完整故事可看。

挑刺练习（批判性阅读）：文件头宣称"幂等可重跑"，但顶部 DROP 清单（8-21 行）只有 14 张表，少了 seckill_order_acceptance——它的 CREATE（252 行）既无 DROP 也无 IF NOT EXISTS。脚本第二次执行必然在 252 行报错 table already exists。结论：读任何脚本都要验真"声明"与"实现"的差距；本项目实际的兜底是 docker 删卷重建（292-293 行注释自述），不是重跑脚本。

6表不是一次成形的，是随阶段"长"出来的

看 git log（backend/ 目录，时间正序），init.sql 的 15 张表分了三个批次才长齐：

阶段 1-3（9c35cc8 起）：用户/商品/寄卖/交易 13 张表——先让主链路能跑
阶段 4（bd06d43 起）：+ seckill_activity 秒杀场次、orders 挂 uk_user_activity
阶段 4 搜索（d1dd46d）：product 挂 FULLTEXT ft_search(name,selling_point,tag) ngram
阶段 4b（8c06144）：+ seckill_order_acceptance 受理登记表（本地消息表简化形态）

这揭示了 schema 设计的真实节奏：先让最小闭环跑起来，玩法域的表后置。每加一张表，都有对应的业务闭环（第 8 课把这条线完整展开）。也正因为后置，才出现了 §5 的 DROP 漏网——增量修改最容易漏改头部清单。

自检测验

先在心里作答，再点开答案。

1. init.sql 声明"无物理外键"，表之间的引用关系靠什么保持一致？

  • A · 应用层逻辑外键加唯一键兜底
  • B · 数据库触发器自动联动两边
  • C · 夜间定时任务扫描修复差异
  • D · 跨表视图把关系物化约束
查看答案与解析

A。引用关系（product_item.product_id → product.id）由应用层代码维护，而业务唯一性由唯一键强制（uk_username、uk_payment_no 等）。B/C/D 这个文件里都不存在。面试展开见 §3 的问答模板。

2. address 表的 default_guard 生成列解决什么问题？

  • A · 保证同一用户只有一个默认地址
  • B · 加速按用户编号查询的速度
  • C · 防止收货人姓名字段超长溢出
  • D · 为每行自动生成默认地址编号
查看答案与解析

A。MySQL 无部分唯一索引，用生成列把"is_default=1 时等于 user_id"编码进 schema，配唯一键强制"每个用户最多一个默认"。并发双击必败一个。B 是索引顺带效果；C/D 与生成列无关。

3. 秒杀种子时间为什么用 DATE_SUB(NOW(), INTERVAL 1 DAY) 而不是写死日期？

  • A · 脚本重跑后活动仍处于正确状态
  • B · 减少种子数据的总行数规模
  • C · 让插入语句执行得更快一些
  • D · 避免日期字段索引发生碎片
查看答案与解析

A。init.sql:263 注释原话："时间用 NOW() 相对表达式——init.sql 幂等重跑后活动仍处对应状态（绝对日期会过期）。"写死 2026-11-01，下个月重跑活动就"过期"了。B/C/D 都不是动机。

4. orders 存 address_snapshot JSON 而不是只存 address_id，为什么？

  • A · 地址日后被改删历史订单仍准确
  • B · JSON 比整数编号占用空间更小
  • C · 前端可以直接渲染省去了解析
  • D · 可以少建一张地址关联中间表
查看答案与解析

A。交易系统的铁律：历史事实必须定格。只存 id，买家改地址后旧订单就"失忆"了。B 明显错误（JSON 更大）；C 是顺带好处；D 答非所问。

5. （挑刺）照原样重跑 init.sql，会在哪张表直接报错？

  • A · seckill_order_acceptance 缺 DROP
  • B · orders 保留字导致建表失败
  • C · address 生成列写法不合法
  • D · product 全文索引语法错误
查看答案与解析

A。顶部 DROP 清单（8-21 行）14 张表，没有 seckill_order_acceptance；252 行的 CREATE 又无 IF NOT EXISTS——二次执行必在 252 行报 table already exists。B 已被 173 行注释绕开（表名用 orders）；C/D 语法均合法。这就是"声明幂等"与"真幂等"的差距。
