0先做闭卷预测

在继续阅读前，拿纸回答三个问题，不知道就明确写“不知道”：

  1. 浏览器请求 http://localhost:8080/api/mall/product/list 时，请求依次经过哪些进程？
  2. 根目录编排与 backend/docker-compose.yml 中，后端应用分别在哪里运行？
  3. docker compose down 与 docker compose down -v 对数据库数据有什么差别？

保留这份预测。学完后对照修正，比直接阅读答案更能暴露真实理解。

1先分清两种运行形态

形态基础设施后端应用入口
全栈容器根目录 Compose 启动 MySQL、Redis、RabbitMQbackend 容器Nginx :8080
本地开发backend/docker-compose.yml本机 mvn spring-boot:run前端网关 :8080，后端 :18080

README.md:28-50；backend/docker-compose.yml:1-7

两套形态解决不同问题：前者让你观察完整部署拓扑，后者便于修改和调试 Java 代码。端口、服务名和启动命令必须连同所在形态一起理解。

2一张运行地图

浏览器
│ http://localhost:8080
▼
web · Nginx
├─ /h5、/admin … → 六个前端应用的静态产物
└─ /api … → http://backend:18080
▼
backend · Spring Boot
├─ mysql:3306 · MySQL
├─ mall-redis:6379 · Redis
└─ mall-rabbit:5672 · RabbitMQ

README.md:81-90；docker-compose.yml:53-96

根编排只把 web 的 8080:80 映射到宿主机。后端、MySQL、Redis 和 RabbitMQ 不直接暴露宿主机端口，而是在 Compose 网络内通过服务名互相访问。

本机开发则不同：backend/docker-compose.yml 把 MySQL 的容器端口 3306 映射为宿主机 13306。因此本机 Java 进程连接 localhost:13306，容器内 Java 进程连接 mysql:3306，两者并不矛盾。

心智模型：localhost 总是“当前网络命名空间里的自己”。在本机终端它是你的电脑；在 backend 容器里它是后端容器自己，不是 MySQL 容器。

3/api 为什么不会丢

Spring Boot 自己配置了 server.servlet.context-path: /api，所以业务接口完整路径是 /api/mall/**。根编排中的 Nginx 接收同源 /api 请求，再转发到 backend:18080。

backend/src/main/resources/application.yml:1-4；README.md:83-89

这解释了为什么“前端静态页面能打开”和“业务接口可用”是两个不同检查：前者只证明 Nginx 能返回文件，后者还依赖 upstream 解析、后端进程、鉴权规则和数据库等链路。

4两类变量占位，不要混为一谈

本项目至少有两层配置解析：

位置例子谁读取作用
application.yml${DB_URL:jdbc:mysql://localhost:13306/…}Spring环境变量存在则用环境值，否则用本机默认值
docker-compose.yml${DB_PASSWORD:-mall-root}Compose变量未设置或为空时，在生成 Compose 模型时采用默认值

backend/src/main/resources/application.yml:9-25；docker-compose.yml:9-12、61-82

根编排还向 backend 容器显式传入 DB_URL=jdbc:mysql://mysql:3306/…，覆盖 Spring 的本机默认值。同一应用不改代码，却能从本机开发切换到容器网络，靠的就是外部化配置。

Compose 官方文档说明：${VAR:-default} 在变量未设置或为空时使用 default；可用 docker compose config 检查插值后的模型。但完整输出可能包含敏感值，课堂反馈不要直接粘贴。

5启动顺序与健康检查

根编排中，backend 等待 MySQL、Redis、RabbitMQ 健康；web 又等待 backend 健康。后端的 Dockerfile 用匿名商品接口执行健康检查。

docker-compose.yml:57-60、94-96；backend/Dockerfile:17-20

Compose 官方语义是：被标记为 service_healthy 的依赖必须先通过自身 healthcheck，再启动依赖它的服务。它比“容器进程已经启动”更有信息量，但仍不是无限保证：

  • 它只反映所配置检查命令的结果，不代表每个业务场景都正确。
  • 后端当前检查商品接口，不等于支付、MQ 消费和结算都已验证。
  • 后续运行时仍可能故障，所以还需要日志、业务验证和恢复手段。

6容器可删，数据未必该删

根编排把 MySQL 数据放在命名卷 mall-mysql-prod-data。Docker 官方 CLI 文档说明：普通 docker compose down 默认删除容器和相关网络，不删除 Compose 声明的命名卷；加上 -v 才会删除这些卷。

docker-compose.yml:18-20、99-100；Docker Compose CLI · down（见主推荐来源旁的链接）

安全边界：down -v 不是“更彻底的重启”。只有明确要永久重置可丢弃的本地数据时才考虑执行。真实环境或含重要数据时，本课不授权执行。

还要区分另一件事：MySQL 的 init.sql 挂载到初始化目录，只在数据目录为空时自动执行。因此“修改 SQL 文件”与“已有数据库被更新”不是同一件事。

7 · 安全实验：观察后端停止与恢复

以下命令在仓库根目录执行。首次构建可能需要较长时间；没有 Docker 环境时保留“未执行”，不要编造输出。

# 1. 只列服务名，不输出展开后的敏感配置
docker compose config --services

# 2. 构建并启动全栈
docker compose up -d --build
docker compose ps

# 3. 验证经 Nginx 到达后端与数据库的匿名接口
curl -f http://localhost:8080/api/mall/product/list

# 4. 只停止后端，不删除容器、网络或卷
docker compose stop backend
docker compose ps

# 5. 再请求一次，记录真实结果；随后启动原容器
docker compose start backend
docker compose ps

等待后端恢复健康后，再执行第 3 步的 curl。你的记录应包含：

  • config --services 是否列出 mysql、mall-redis、mall-rabbit、backend、web；
  • 后端停止前后，同一请求的实际差异；
  • 后端启动后为什么不能只凭一次 ps 就立即宣布恢复，还要再看健康状态和业务响应。

如果命令失败，保留原始错误并停在当前步骤。先定位，不要同时改多份配置，也不要用 down -v 掩盖问题。

自检测验

先独立选择，再展开解析。每题四个选项均为相同字数，答案位置不作为线索。

1. 全栈容器中，商品接口的正确路径是？

  • A · 浏览器→Nginx→后端
  • B · 浏览器→后端→Nginx
  • C · 浏览器→Nginx→前端
  • D · 浏览器→前端→Nginx
查看答案与解析

A。Nginx 是唯一公开入口，静态文件与 /api 在这里分流，后者被转发到 Spring Boot。

2. Compose 变量未设置或为空时，${VAR:-default} 会？

  • A · 采用配置默认值
  • B · 采用空字符串值
  • C · 启动时报错退出
  • D · 忽略这一项配置
查看答案与解析

A。冒号加短横线的形式在变量未设置或为空时使用默认值。只有 ${VAR-default} 才只针对“未设置”。

3. 普通 docker compose down 默认会？

  • A · 删除容器保留卷
  • B · 删除容器与数据
  • C · 仅停容器不删除
  • D · 删除镜像保留卷
查看答案与解析

A。普通 down 删除容器；命名卷默认保留。stop 才只停止容器，-v 才明确要求删除 Compose 声明的命名卷。

4. depends_on: service_healthy 会？

  • A · 等待依赖健康检查通过
  • B · 等待依赖进程启动成功
  • C · 等待依赖镜像构建完成
  • D · 等待依赖端口对外开放
查看答案与解析

A。它等待所配置 healthcheck 报告健康。进程启动对应较弱条件，健康检查也不等于全部业务场景已验收。
