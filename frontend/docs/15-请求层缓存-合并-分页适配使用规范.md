# 请求层缓存 / 合并 / 分页适配 使用规范

> **文档版本**：v1.1.0 | **最后更新**：2026-11-04
> **能力来源**：`packages/shared/src/api/cache.ts` + `packages/shared/src/api/request-merger.ts` + `packages/shared/src/api/page-adapter.ts` + `packages/shared/src/api/mock-guard.ts`（CHANGELOG 未记录，2026-07-24 审计补齐文档；2026-09-04 修正 mock-guard 用法描述 + 同步测试用例数；2026-11-04 同步 request-merger 审查修复——signal 两路链接 / mergeKey 不可归一化负载退化 / 窗口语义声明，见 §2）

---

## 📋 三件套速览

| 能力            | 文件                | 解决什么问题                                  | 默认行为             |
| --------------- | ------------------- | --------------------------------------------- | -------------------- |
| **Cache**       | `cache.ts`          | 防重复请求（同一 GET 在 TTL 内复用结果）      | 默认关闭，按需开     |
| **Merge**       | `request-merger.ts` | 时间窗口内同参请求合并（同 key 共享 Promise） | 仅 GET/HEAD 默认合并 |
| **PageAdapter** | `page-adapter.ts`   | 后端分页字段名约定不一致自动适配              | 默认 v2 后端约定     |

三件套都是**可插拔能力**：业务侧零感知，组合在 `http.ts` 拦截器链 + `request<T>()` 中。

## 1. 内存缓存（Cache）

### 用法

```ts
import { request } from '@api/http'

const data = await request<Pagination<Item>>({
  url: '/item/list',
  method: 'get',
  params: { page: 1, pageSize: 20 },
  usePageAdapter: true,
  cache: { ttl: 30 }, // 30 秒内同 url + params 不重复请求
})
```

### 适用场景

- **字典数据**（`api/modules/dict.ts` 默认 `cache: { ttl: 30 }`）
- **配置数据**（站点设置、权限模板）
- **首页聚合数据**（仪表盘 5 张卡片，30s 内用户刷新不重发）

### 失效方式

```ts
import { cacheClear } from '@api/cache'

// 写操作后清空相关 GET 缓存
async function createItem(data: Item) {
  const result = await request({ url: '/item', method: 'post', data })
  cacheClear('GET|/item|') // 清空所有 /item 开头的 GET 缓存
  return result
}
```

### ⚠️ 不适用场景

- **写操作**（POST/PUT/DELETE 自动跳过）
- **实时数据**（订单状态、消息列表）
- **用户私有数据**（跨用户共享缓存可能泄露，见 `@api/cache` 的"跨用户/会话共享"注释）

## 2. 请求合并（Merge）

### 用法

```ts
import { request } from '@api/http'
import { withMerge } from '@api/request-merger'

// 方式 1：模块级预包装（推荐）
const mergedRequest = withMerge(request)
const users = await mergedRequest({ url: '/user/list', method: 'get' })

// 方式 2：单次配置 directive
await request({ url: '/user/1', method: 'get', merge: 'never' }) // 临时禁用
await request({ url: '/user/1', method: 'put', data, merge: 20 }) // 20ms 合并窗口
```

### 默认行为

- **仅 GET/HEAD 合并**（写操作白名单，避免掩盖真实失败链路）
- **窗口 50ms，从首个请求 settle 起算**（2026-11-04 语义声明：窗口期内失败结果同样被
  后续同 key 请求共享——缓存失败而非仅去重；需要重试语义的请求应设 `merge: 'never'`）
- **同 method + url + params + data 归一化为同一 key**（Date 按时间戳参与归一化；
  **FormData / Blob / URLSearchParams / 循环引用无法安全归一化，mergeKey 返回 null、
  该请求退化为不合并**——错合并风险大于漏合并损失，2026-11-04 审查修复）
- **调用方 signal 被链接保留**（2026-11-04 审查修复）：`fn({ ...config, signal })` 不再
  覆盖调用方自传 signal，经 `linkAbort` 两路链接——调用方取消与本地控制器任一中止
  都会中断底层请求（见 `cancel.ts`）

### 适用场景

- **仪表盘首屏**：5 张卡片同时 onMounted 触发 → 合并为 1 次请求（节省 4 次）
- **批量查询**：列表 + 详情同时加载 → 同 key 自动合并

### ⚠️ 不适用场景

- **写操作**：POST/PUT/DELETE 默认不合并（避免掩盖真实失败）
- **跨窗口长耗时合并**：50ms 窗口已过期仍可触发重复请求（这是设计取舍，不是 bug）

## 3. 分页适配（PageAdapter）

### 用法

```ts
// 业务侧无需关心字段名——只需传语义化字段
const page = await request<Pagination<Item>>({
  url: '/item/list',
  method: 'get',
  params: { page: 1, pageSize: 20, keyword: 'foo' }, // 项目语义
  usePageAdapter: true, // 拦截器自动转后端字段名
})
// 实际请求参数变为 { pageIndex: 1, pageSize: 20, keyword: 'foo' }
// 响应自动解包为 { list: [...], total: 100, page: 1, pageSize: 20 }
```

### 默认约定（v2 后端）

| 语义          | 默认字段名  | 配置项                   |
| ------------- | ----------- | ------------------------ |
| 请求 page     | `pageIndex` | `request.pageField`      |
| 请求 pageSize | `pageSize`  | `request.pageSizeField`  |
| 响应 list     | `records`   | `response.listField`     |
| 响应 page     | `current`   | `response.pageField`     |
| 响应 pageSize | `size`      | `response.pageSizeField` |
| 响应 total    | `total`     | `response.totalField`    |

### 自定义后端字段名

```ts
// src/main.ts（应用启动时调一次）
import { configurePaginationAdapter } from '@api/page-adapter'

configurePaginationAdapter({
  request: { pageField: 'p', pageSizeField: 'limit' },
  response: { listField: 'items', pageField: 'page_num' },
})
```

### ⚠️ 不适用场景

- **非分页接口**（如 GET /user/1 返回单条）：不传 `usePageAdapter: true` 即可
- **GraphQL 接口**：分页协议完全不同（cursor-based）

## 🎯 最佳实践组合

```ts
// 仪表盘首屏：cache + merge + pageAdapter 三件套全开
const stats = await request<Pagination<StatItem>>({
  url: '/portal/overview',
  method: 'get',
  params: { page: 1, pageSize: 5 },
  usePageAdapter: true,
  cache: { ttl: 30 },
})
// 30s 内 5 张卡片同 onMounted 触发 → 合并为 1 次请求 + 30s 复用
```

## 🆚 决策表

| 场景         | 用 cache   | 用 merge               | 用 pageAdapter |
| ------------ | ---------- | ---------------------- | -------------- |
| 字典数据     | ✓ ttl=30   | —                      | —              |
| 仪表盘聚合   | ✓ ttl=30   | ✓                      | —              |
| 列表分页     | 可选       | ✓（同 onMounted 并发） | ✓              |
| 详情（单条） | —          | —                      | —              |
| 写操作       | ✗ 自动跳过 | ✗ 默认仅 GET           | —              |
| 实时数据     | ✗          | ✗                      | —              |

## 🛡️ Prod 防御层：mock-guard 扩展点

> **问题**：vite-plugin-mock 由 `@vv/config` 工厂 `packages/config/src/create-vite-config.ts` 中 `enable: VITE_USE_MOCK !== 'false'` 控制（2026-07-27 切换；配置单源在工厂，不在各 app vite.config.ts）。prod 模式下若代码残留 mock 数据，会带入 prod 包。

**项目方案**：`packages/shared/src/api/mock-guard.ts` 提供 prod 模式防御层扩展点。当前实现保留为**最小骨架**（兜底由 Vite 构建时 tree-shake 保证），未来需要更强运行时校验时再扩展。

### 当前实现

```ts
// packages/shared/src/api/mock-guard.ts（最小骨架）
export function assertNoMockInProd(): void {
  // vite-plugin-mock 仅在 dev 服务生效；prod 构建自然剔除 mock 模块
  // 此函数保留为防御层扩展点——如未来需要运行时校验（如扫描 import.meta.glob），
  // 可在此实现具体逻辑
  void 0
}
```

### 调用方式（推荐）

```ts
// 调用已收敛下沉至 @vv/shared bootstrapApp 工厂（packages/shared/src/app-mount.ts:114），
// app 侧无需手写——工厂在 brandColor/title 之后统一调用 assertNoMockInProd()
// （以下为工厂内代码的语义说明，非 app 接入代码）
import { assertNoMockInProd } from '@api/mock-guard'

if (import.meta.env.PROD) {
  assertNoMockInProd()
}
```

> **注意**：旧版文档描述的 `setupProdMockServer({ interceptUrls: [] })` API **不存在**——该 API
> 未实现也未在 `mock-guard.ts` 中导出。如果未来需要"prod 环境演示 / 离线部署"等需要 MSW 拦截
> 的场景，应新增 `setupProdMockServer()` 函数并在 `mock-guard.ts` 单独导出，
> 不要使用本文档示例代码（避免误导）。

### 启用决策

| 场景                          | 是否调用 `assertNoMockInProd` |
| ----------------------------- | ----------------------------- |
| **默认**（prod 走真实接口）   | ✅ 入口处调用一次（兜底）     |
| prod 环境演示（不能连真后端） | ❌ 演示场景不需要此函数       |
| 离线部署演示包                | ❌ 同上                       |
| CI 自动化测试 prod 包         | ✅ 视场景而定                 |

### 与 vite-plugin-mock 的关系

| 工具                 | 启用场景          | 配置位置                                                                                  |
| -------------------- | ----------------- | ----------------------------------------------------------------------------------------- |
| **vite-plugin-mock** | dev 环境          | `packages/config/src/create-vite-config.ts`（@vv/config 工厂）                            |
| **mock-guard**       | prod 防御层扩展点 | `packages/shared/src/app-mount.ts`（工厂内调用）+ `packages/shared/src/api/mock-guard.ts` |

### 注意事项

- 默认 prod 模式不启用任何 mock，所有请求走真实接口
- 当前 `assertNoMockInProd()` 为 noop（仅占位），prod 安全靠 Vite 构建配置保证（mock 模块 tree-shake 剔除）
- 如未来需要"运行时扫描 import.meta.glob" 等强校验，扩展 `mock-guard.ts` 即可，不影响现有调用方
